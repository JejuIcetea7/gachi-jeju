대표 실패 5건의 자동 통과는 7/10에서 9/10으로 올랐지만, 기존 실패 탐색 표본 전체에서는 40/50에서 27/50으로 떨어졌다. 평균 응답시간도 19.7초에서 26.6초로 늘었다. 이 표본에서는 사용자 요청을 전반적으로 더 잘 처리하게 됐다고 보기 어렵다.

## 실험 방법

- **기존 요청 재실행**. 최초 실험의 50개 요청 기록 각각에 저장된 질문, 선택 조건, 대화 이력, 기존 일정과 기준 날짜를 그대로 사용했다. 이전 단계의 답변까지 고정했으므로 한 번의 후속 요청이 얼마나 잘 처리되는지를 비교한다. 50건에는 반복 요청이 포함돼 있다.
- **대표 실패 반복 실험**. 위 표와 관련된 기존 실패 5건을 골라 이전 코드를 별도 경로에 복원하고 현재 코드와 같은 로컬 데이터로 실행했다. 요청마다 각 버전을 두 번 실행했다. 전체 50건의 비교와 별도로 집계했다.
- 두 버전 모두 실제 모델 `gpt-6-luna`, 추론 설정 `low`, 실제 지도 서비스를 사용했다. 채팅 API가 응답할 때까지의 시간에 내부 재시도도 포함했다. 호출 시각과 실시간 교통, 모델 답변의 변동은 통제할 수 없다. 일부 요청을 동시에 실행했으므로 응답시간에는 동시 실행 부하도 포함된다.
- 자동 통과는 두 버전의 응답에 같은 현재 평가기를 적용해 HTTP 상태, 요청에 맞는 응답 유형, 일정 조건과 조회 근거 등을 판정한 값이다. 자연어 답변의 정확성은 대표 실패 5건에서 별도로 살폈다. 비용은 청구 금액 대신 모델 사용 기록의 입력·출력 토큰으로 비교한다.

## 전체 비교에서 드러난 문제

- 현재 버전은 7건에서 “체류시간을 적용할 장소 이름과 분 수를 함께 알려 주세요”라고 답했다. 예를 들어 사용자는 이미 수목원 체류 90분 안에 휴식 30분을 포함하라고 했는데도 수정된 일정이 나오지 않았다. 가장 먼저 재현할 문제다.
- 교통수단만 바꾸거나 방문 순서를 바꾼 뒤 채팅에서는 변경했다고 안내하면서 수정 일정 객체를 반환하지 않은 사례가 있었다. 화면에 전달된 일정까지 확인해야 하는 이유다.
- 현재 50건의 HTTP 오류는 500 두 건, 502 세 건이었다. 현재 버전의 모델·도구·토큰 평균에는 기록이 없는 두 건을 제외한 48건이 포함됐다.
- 대표 반복 실험에서는 점심 추가가 두 번 모두 성공했지만, 같은 질문의 전체 재실행 회차에서는 일정 검증 오류가 발생했다. 세 회차를 합치면 현재 버전도 2/3 성공이다.
- 기대 결과가 일정 생성인 사례에서 확인 질문이나 안전한 보류도 자동 실패로 집계된다. 이 표본은 실패 탐색용이며, 전체 사용자의 성공률로 환산하기 어렵다. 요청 50건의 역사적 비교에는 운영 시점 차이가 있고, 같은 시점의 비교는 대표 요청 5건으로 한정했다.

## 실험 자료

프로젝트 로컬의 `outputs/chat_eval/paired-20261119/`에 입력 목록(`inputs.json`), 건별 자동 판정(`scores.json`), 실제 요청·응답과 도구 호출 기록을 보관했다. 파일명은 `버전-반복번호-입력번호.json` 형식이며 0은 전체 50건 재실행, 1과 2는 대표 사례 반복이다. 같은 폴더의 `runtime.patch`는 기준 커밋에서 실험 당시 백엔드·실행 스크립트까지의 변경을 담는다. SHA-256은 `1f0f2700fe46e4b868d5329da2c1bd42ce1a913cf185c68821adbe9fc38873e1`이다.

## 프롬프트 정리 후 제한 검증

같은 날 대화형 Agent 지침을 역할과 목표 → 행동 지침 → 처리 예시 → 입력 정보 순서로 다시 작성했다.
처리 절차별로 규칙을 모으고, 기본 일정 생성 지침을 덧붙이던 중복을 제거했다.
최종 전달되는 고정 지침은 15,875자에서 8,533자로 46.2% 감소했다. 문자 수 기준이며 모델 입력 토큰의 감소율과 동일하지 않다.
일정에 영향을 주는 교통·순서·숙소 변경은 전체 일정표를 반환하고, 설정만 바꾸는 응답은 사용자의 명시적 요청에 적용하도록 정리했다.

동일한 입력 파일의 6건을 실제 모델·지도 API로 각 1회 실행했다. 모델 설정과 서버 검증 코드는 기존 실험 상태를 사용했다.
자동 판정 통과는 4/6이다. 이전 현재 버전 재실행에서 해당 6건은 1/6이 통과했다. 소수 사례의 단일 회차 결과이며 반복 성공률과 전체 50건의 개선율은 아직 측정하지 않았다.

## 숙소 취소의 일정 반환 보완

숙소 추가·변경·삭제 등 일정 수정 행동에 새 일정이 있으면 설정 전용 changed_options 표시를 비우고 기존 전체 검증을 진행하도록 보완했다.
같은 숙소 취소 요청을 실제 모델·지도 API로 두 번 실행해 두 번 모두 관광지와 기간을 유지한 수정 일정이 반환되는 것을 확인했다.
기록은 로컬 실험 폴더의 `fix-1-6.json`, `fix-2-6.json`이다. 이 결과는 해당 요청의 제한 검증이다.

휴식 요청은 사용자의 지시에 따라 이번 변경에서 제외했다. 이를 위해 추가했던 원문 인용 피드백과 체류 대상 연결 수정도 되돌렸다.
`fix-1-8.json`, `fix-2-8.json`은 되돌리기 전 중간 실험 기록이며 현재 코드의 검증 결과로 사용하지 않는다.

## Luna high의 기존 실패 요청 재실행

현재 프롬프트와 숙소 취소 처리 보완을 적용한 상태에서 모델을 GPT-6 Luna high로 설정했다.
이전 요청의 질문·대화·일정·기준 날짜를 복원해 6건을 실제 모델·지도 API에서 각 1회 실행했다.
사용자 지시에 따라 휴식 요청은 제외했다. 서버·프롬프트 변경도 적용된 상태이므로 low와 high의 성능 차이만으로 해석할 수 없다.

| 요청 | 결과 | 응답시간 |
|---|---|---:|
| 숙소 취소, 관광 유지 | 통과 | 47.7초 |
| 박물관 90분 유지, 12~13시 점심 추가 | 통과 | 56.3초 |
| 여행 날짜만 하루 뒤로 이동 | 실패 | 82.2초 |
| 도보를 자동차로 변경 | 통과 | 30.9초 |
| 첫날 제주신라호텔 선택 | 통과 | 55.5초 |
| 함덕→한림공원→협재 순서 변경 | 통과 | 37.0초 |

자동 판정은 5/6 통과다. 통과한 응답은 최종 일정의 장소·순서·체류시간과 경로 연결을 함께 검토했다.
평균 응답시간은 51.6초다. 각 1회 실행한 선택 표본이므로 전체 성공률과 반복 안정성은 추가 측정이 필요하다.

실패한 날짜 변경 요청은 사용자가 11월 21~22일을 명시했고 모델도 두 번 모두 start_date=2026-11-21을 반환했지만,
서버가 “입력 근거 없이 출발 날짜 조건을 변경할 수 없습니다”라고 거부했다.
이 요청의 실패 지점은 서버의 날짜 조건 검증이며 모델 변경만으로 해결되지 않았다.

원본 기록은 로컬 실험 폴더의 `high-1-입력번호.json`, 자동 판정은 `high-scores.json`에 저장했다.

## 여행 날짜 변경 보완

Agent 내부 응답에 trip_date_change를 추가해 여행 전체의 날짜 변경 의도와 날짜 원문을 전달한다.
서버는 그 구절이 현재 요청에 포함되는지 확인하고 원문에서 날짜·여행 일수를 계산해 기존 검증에 사용한다.
과거 응답은 필드 없이 기존 해석을 사용한다. 개별 관광지 방문일 변경은 여행 출발일 변경과 구분한다.

첫 실제 검증 두 회차는 날짜를 읽었으나 유지·변경 행동의 근거 구절이 겹쳐 다른 검사에서 차단됐다.
서로 다른 행동의 근거를 구분하도록 지침을 보완한 뒤 같은 요청을 두 번 실행해 두 번 모두 자동 평가를 통과했다.
11월 21~22일의 2일 일정, 기존 관광지의 상대 일차와 관람시간, 선택한 숙소가 유지되는 것도 실제 응답으로 확인했다.
기록은 로컬 실험 폴더의 `date-1-11.json`부터 `date-4-11.json`이며 최종 지침 결과는 3·4회차다.
자동 테스트는 1,220개가 통과했다. 전체 50건의 반복 평가는 이번 수정에서 실행하지 않았다.
