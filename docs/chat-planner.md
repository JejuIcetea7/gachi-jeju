# 대화형 여행 플래너와 이동 경로 지도

최종 자동 검증일: 2026-11-19
최종 UI 수동 검증일: 2026-11-18 (숙소 선택·채팅 변경, 1박 2일→당일 축소·지도와 일정 갱신·새로고침 복원, 사용자 확인)
기존 이동 API·경로 지도 수동 검증일: 2026-11-11

대화형 Agent의 고정 지침은 역할과 목표, 행동 지침, 처리 예시, 입력 정보 순서로 작성합니다.
행동 지침은 요청 판단 → 기존 상태·변경 조건 확인 → 도구 조회 → 일정 구성 → 정보 부족·실패 처리 → 최종 응답 순서입니다.
기존 일정의 방문일·체류시간을 보존하는 기준과 운영·시설·이동을 이번 도구 조회로 확인하는 기준을 구분합니다.
일정에 영향을 주는 변경은 전체 일정표를 반환하고, 설정만 바꾸는 응답은 사용자가 명시한 경우에 적용합니다.
일정 생성·수정 행동과 새 plan이 함께 있으면 changed_options를 비우고 일정 검증을 진행합니다. 설정 변경 표시만으로 새 일정을 제거하지 않습니다.

자연어 대화와 선택 옵션으로 제주 여행 일정을 생성·수정합니다.
자동차·도보·대중교통 경로와 날짜별 일정표를 함께 표시합니다.

여행 전체의 날짜를 변경할 때 Agent의 내부 응답 trip_date_change에 변경 의도와 날짜가 포함된 사용자 원문을 기록합니다.
서버는 해당 구절이 현재 요청에 있는지 확인하고, 원문 날짜로 출발일과 양 끝을 포함한 기간을 계산해 일정 조건과 대조합니다.
개별 관광지 방문일 변경과 날짜 문의에는 이 필드를 사용하지 않습니다. 기존 응답에서 필드가 없으면 종전 날짜 해석을 적용합니다.

2026-11-19 모델 설정은 GPT-6 Luna, 추론 수준 high입니다. 공통 설정을 사용하는 /chat과 /plan에 적용합니다.
앞서 수행한 개선 전후 비교와 프롬프트 실험의 추론 수준은 low입니다.
현재 Luna high의 35건 종합 평가와 발견한 결함·응답시간은 [종합 점검 보고서](experiments/0012-luna-high-comprehensive-audit.md)에 기록했습니다.

통합 WebP 사진은 CloudFront 주소 목록으로 연결합니다. 설정과 검증 범위는 [사진 클라우드 연결](place-photo-cloud.md)을 참고합니다.
한림공원 일정의 사진·설명 표시와 중복 설명 정리를 사용자에게 확인받았습니다.

## 1. 제공 기능

| 항목 | 동작 |
|---|---|
| 화면 구성 | 위쪽 여행 옵션, 아래쪽 대화창을 표시합니다. 지도·일정표는 오른쪽에서 열리는 사이드바에 표시하며, 넓은 화면에서는 사이드바 왼쪽 경계를 움직여 너비를 조절합니다. |
| 여행 조건 | 출발지, 출발일·마지막 날, 이동수단, 보조기구, 여행 종류, 필요한 접근 조건을 선택합니다. 옵션 없이 대화로 시작할 수도 있습니다. |
| 대화 | 요청과 선택 옵션을 함께 반영합니다. 정보가 부족하면 질문하고, 후속 요청으로 전체 일정을 수정합니다. |
| 지도·일정표 | 출발지와 방문 장소, 실제 조회한 이동 경로를 표시합니다. 여러 날 일정은 일차별로 전환하며, 확인사항은 일정표 아래에 표시합니다. |
| 장소 상세·사진 | 장소명을 누르면 일정별 접근성 메모, 시설·추천 원문, 지점별 동선 설명과 사진을 확인합니다. 정보·사진은 별도로 조회하며 사진이 없어도 상세 정보를 표시합니다. |
| 방문 전 확인 | 방문 카드에서 일정에 포함된 장소별 메모를 두 항목까지 보여 줍니다. 메모가 더 있으면 상세 창에서 전체를 확인할 수 있습니다. |
| 버스 탑승 안내 | 이동 행에서 승차 정류장, 버스 노선, 하차 정류장과 이동 정거장 수를 확인합니다. 도보·환승 구간은 순서를 유지합니다. |
| 숙소 미정·선택 | 숙소가 미정이어도 여러 날의 관광 일정을 먼저 만듭니다. 숙박일별 마지막 방문지 주변 후보를 고르면 숙소 전후 이동과 시간을 다시 계산합니다. |

**방문 순서와 동선 효율**

`suggest_visit_order`는 DB 여행지 1~12곳의 좌표로 직선거리 기준 순서 후보를 계산합니다.
고정 장소의 원래 위치를 유지하고 다른 장소도 해당 고정 장소를 넘어 이동하지 않습니다.
각 고정 장소 사이 구간에서 1m 이상 줄어들 때만 순서 후보를 바꾸며 장소·방문일·시간표를 직접 수정하지 않습니다.

Agent는 가까운 권역을 날짜별로 묶고 각 날짜의 실제 출발·숙소·귀환 위치로 비교합니다.
대화형 실행에서는 `day`와 그날의 `place_ids`, `origin_ref`·`destination_ref`를 전달합니다.
숙소 미정인 경계는 null로 두며 센터나 전날 관광지로 대신하지 않습니다.

| 위치 참조 | 의미 |
|---|---|
| `place:P001` | DB 장소 ID에 대응하는 좌표입니다. 외부 숙소 검색 ID를 대신 사용하지 않습니다. |
| `departure` | 이번 요청에서 이름과 좌표가 확인된 원래 출발지입니다. |
| `stay:N` | 이번 요청 options에 전달된 N번째 숙박일의 선택 위치입니다. 채팅에서 새 숙소를 조회해도 자동 변경되지 않습니다. |
| `found:...` | 이번 Agent 실행에서 성공한 위치 조회가 반환한 참조입니다. 다음 실행에서 재사용하지 않습니다. |

새 숙소로 변경하면 조회 응답의 새 참조를 실제 이동뿐 아니라 해당 날짜들의 순서 비교에도 사용합니다.
서버는 좌표를 변환해 기존 이동 도구를 호출하고 결과에 출발·도착 장소를 함께 표시합니다.
기본 교통 도구의 직접 좌표 호출 방식은 유지합니다.
시간이나 이동수단을 바꿔도 확정된 출발 위치를 사용합니다.
확정된 출발지와 같은 이름만 다시 조회하면 기존 좌표를 반환합니다.
같은 장소의 다른 입구나 주소로 출발지를 바꾸면 해당 위치를 새로 조회합니다.

방문 장소의 이동·순서 비교에는 같은 시도의 성공한 `get_place_details`를 선행 조건으로 둡니다.
최종 일정도 이번 시도의 상세 조회 근거를 검사하며, 이전 대화나 실패한 시도로 대신하지 않습니다.
하루 전체 장소를 비교한 경우에는 최종 출발지·숙소·귀환 위치에 맞는 성공 근거가 있는지 대조합니다.
이전 위치를 탐색한 비교가 있어도 새 위치로 유효한 비교를 수행했다면 허용합니다.
작은 구간으로 나눈 비교와 도구 호출이 없는 기존 응답에는 이 경계 대조를 적용하지 않습니다.

최종 이동은 선택한 교통수단의 실제 도구로 조회하고 시간·휴무·운영시간·접근 조건·경로를 검증합니다.
고정 조건이나 실제 이동시간 때문에 최종 순서가 직선거리 제안과 다른 것은 허용합니다.
서버가 모든 요청의 순서를 강제로 재배치하거나 최단시간·버스·휠체어 최적성을 보장하는 기능은 아닙니다.

자동차 당일 순서 자유·고정 사례는 [실험 0007](experiments/0007-route-efficiency.md),
1박 2일 권역 배치·숙소 선택·채팅 변경과 사용자 화면 확인은 [실험 0008](experiments/0008-route-efficiency-multiday.md)에 기록했습니다.

**날짜와 기간**

- 출발일과 마지막 날을 모두 포함해 여행 일수를 계산합니다.
- 같은 날짜는 당일이며, 5일은 4박 5일로 표시합니다.
- 현재 대화형 화면과 `/chat`에는 기존 3일 상한을 적용하지 않습니다.
- 잘못된 날짜, 역순 날짜, 달력 범위를 벗어나는 조합은 거부합니다.
- 달력에서는 한국 시간 기준 오늘보다 이전 날짜를 선택할 수 없습니다.

출발일을 변경하면 선택한 마지막 날을 유지하면서 기간을 다시 계산합니다.
새 출발일이 마지막 날보다 늦으면 마지막 날을 비워 다시 선택하도록 합니다.

시작·종료 시각, 중간 휴식, 여행 마무리는 선택 옵션에서 제외했습니다.
필요하면 자연어로 요청합니다.
귀환 요청 처리를 위해 API의 `return_to_origin` 필드는 유지합니다.

**당일 일정의 숙박 요청**

식사·숙박을 언급하면 기존 모델이 답변과 함께 대상, 행동, 근거가 된 사용자 원문을 반환합니다.
당일 여행에서는 장소·이동 도구를 열기 전에 같은 모델이 이번 발화와 최근 대화로 숙박 변경 여부를 먼저 판단합니다.
숙박 추가·변경을 원하고 기간 연장에 아직 동의하지 않았으면 검색 없이 1박 2일 연장 여부를 묻습니다.
호텔 주소만 물으면 같은 요청에서 위치를 조회할 수 있습니다. 숙박 변경 의도가 모호하거나 원문 근거가 다르면 검색 없이 확인합니다.
이 판단에는 모델 호출 한 번이 들며 호출·토큰 집계에 포함합니다. 동일 요청의 자동 재시도에서는 앞선 판단을 반복하지 않습니다.
숙박 비용만 묻거나 식사를 선택 사항으로 두는 대화는 기존 지도와 일정을 보존합니다.
“점심은 안 넣어도 돼”는 기존 식당을 유지합니다. “점심을 빼줘”는 삭제할 기존 방문을 확인하고,
식당이 여러 곳이라 대상을 특정할 수 없으면 방문일이나 식당 이름을 되묻습니다.
관광 일정 수정도 함께 요청하면 문의의 가정·시각을 제외하고 실제 변경 요청만 일정 검증에 사용합니다.
모델이 과거 턴의 문장을 이번 요청으로 잘못 인용하면 재시도 한도 안에서 최신 메시지를 한 번 다시 확인합니다.
근거를 확인할 수 없으면 변경할 항목을 되묻고 기존 일정을 보존합니다.
확인 질문과 짧은 거절은 `plan: null`을 반환합니다. 바로 앞 기간 질문에 대한 짧은 거절은 모델 호출 없이 처리합니다.
바로 앞의 기간 질문에 동의하면 1박 2일 조건과 원래 숙소 요청을 Agent에 전달합니다.
새 숙소는 이번 실행의 위치 조회 근거로 계속 검사합니다.

마지막 날 관광지 방문이 없어도, 전날 일정과 선택 숙소·출발지가 확인되고 귀환을 요청했다면
숙소→출발지 이동을 포함해야 합니다. 귀환 이동만 있는 날짜도 허용합니다.
모든 숙박일의 숙소가 선택돼 있는데 숙소 미정·미제공으로 설명한 경우도 검사합니다.
검증 실패는 기존 최대 1회 재생성에 연결합니다.

Python 전체 1,055개와 당일→1박 2일 변경·귀환 전용 날짜의 화면을 확인했습니다.
동작과 확인 범위는 [실험 0009](experiments/0009-chat-lodging-period-clarification.md)에 기록했습니다.

**기간 축소와 숙소 선택 취소**

기간 축소가 고정 방문일과 충돌하면 변경할 조건을 먼저 질문하도록 지시합니다.
확인 전에는 현재 옵션을 유지하고 `plan: null`로 답해 기존 지도와 일정을 보존합니다.
기존 일정을 유지한다는 이유로 `current_plan`을 새 `plan`에 복사해 반환하지 않습니다.

기간 축소·숙소 선택 취소·충돌 확인 후 축소의 대표 연속 대화를 검증했습니다.
삭제한 범위 밖 일차를 귀환 일차로 오인하는 문제를 보완하고,
출발지 이름 앞뒤에 시각을 쓰는 명시적인 도착 설명도 최종 시간표와 대조합니다.

Python 전체 1,074개와 마지막 PS03 재채점이 통과했습니다.
당일 축소 후 지도·일정과 새로고침 복원은 사용자 화면 확인을 받았습니다.
실패 기록과 확인 범위는 [실험 0010](experiments/0010-chat-period-shortening.md)에 정리했습니다.

**출발지와 접근성**

기본 출발지는 제주빅데이터센터입니다.
센터 주소 설정값은 `제주특별자치도 제주시 첨단로 241`입니다.
`/chat`에서 출발지가 제주빅데이터센터이고 좌표 두 값이 모두 비어 있으면,
서버는 확인된 센터 좌표를 넣어 Agent에 전달합니다.
요청에 좌표가 있으면 그 좌표를 사용합니다.

여행 옵션의 ‘출발지 변경’은 지도 없이 검색 입력창과 결과 목록을 표시합니다.
장소를 검색하면 최대 5개의 장소명과 주소를 보여 줍니다.
결과를 누르면 해당 장소의 이름·주소·좌표를 출발지에 반영합니다.
검색어 입력만으로는 출발지가 변경되지 않습니다.

‘센터에서 출발’과 ‘현재 위치 사용’ 버튼은 같은 너비로 나란히 표시합니다.
센터·현재 위치·검색 결과로 출발지를 선택해도 변경 영역은 열린 상태를 유지합니다.
선택 완료 시 이전 검색 결과 목록을 초기화하고 선택한 출발지 이름을 표시합니다.
선택한 출발지는 같은 탭에서 새로고침해도 복원합니다.

검색은 카카오 지도 SDK의 장소 검색 기능을 사용하지만,
출발지 선택 영역에 지도나 마커를 생성하지 않습니다.

‘여행지 자료 등록’은 DB에 등록된 장소라는 뜻입니다.
장소 전체의 무장애 이용을 보장하는 표시는 아닙니다.

## 2. 개발 실행

Python 3.12 가상환경 `.venv`와 Node.js·npm을 사용합니다.
아래 명령은 프로젝트 루트에서 실행하는 Windows CMD 기준입니다.

**최초 설치 또는 의존성 변경 시**

```cmd
.venv\Scripts\python.exe -m pip install -r requirements.txt
npm ci
npm --prefix frontend ci
```

루트와 프론트는 각각의 `package.json`과 잠금 파일을 사용합니다.

**환경변수**

| 파일 | 변수 |
|---|---|
| 루트 `.env` | `KAKAO_REST_API_KEY`, `OPENAI_API_KEY` |
| `frontend/.env.local` | `VITE_KAKAO_MAP_KEY`: 지도 SDK용 JavaScript 키 |

실제 키는 Git에 포함하지 않습니다.
지도 앱의 허용 도메인에 `http://localhost:5173`을 등록합니다.
교통·LLM API 키는 백엔드에서 사용합니다.

**백엔드·프론트 통합 실행**

```cmd
.venv\Scripts\activate.bat
npm run dev
```

루트 실행 스크립트가 백엔드와 프론트를 함께 실행합니다.
백엔드는 활성화한 Python 환경을 사용하며,
실행 명령에 `-X utf8`을 적용합니다.

서버를 실행한 터미널은 켜 둡니다.
lint와 build 명령은 개발 서버를 실행하지 않습니다.

| 주소 | 용도 |
|---|---|
| `http://localhost:5173` | 프론트 화면 |
| `http://127.0.0.1:8000/docs` | 자동 API 명세 |
| `http://127.0.0.1:8000/health` | 백엔드 상태 확인 |
| `http://localhost:5173/api/health` | 프론트 프록시를 통한 상태 확인 |

Vite 개발 서버는 `/api` 요청을 백엔드로 전달하면서 접두사를 제거합니다.
환경변수를 변경하면 해당 개발 서버를 재시작합니다.

## 3. 대화·장소 상세·사진·숙소 검색 API

**대화 요청**

브라우저는 `POST /api/chat`, 백엔드는 `POST /chat`을 사용합니다.
기존 `POST /plan`의 규격은 [기존 API 명세](api.md)를 참고합니다.

선택 헤더 `X-Chat-Request-ID`에는 소문자 UUID4를 지정합니다.
프론트는 전송할 때마다 새 식별자를 만들며, 재전송에도 이전 식별자를 사용하지 않습니다.
헤더가 없으면 서버가 식별자를 생성하므로 기존 클라이언트도 요청할 수 있습니다.

최소 요청 예시입니다.

```json
{
  "message": "제주에서 산책할 만한 곳을 알려 주세요."
}
```

사용자 메시지는 한 번에 1~1,000자입니다.

| 요청 필드 | 내용 |
|---|---|
| `message` | 현재 사용자 요청입니다. |
| `options` | 현재 선택 조건입니다. 생략할 수 있습니다. |
| `history` | 이전 대화입니다. 프론트는 전송 완료된 최근 20개 메시지를 전달합니다. |
| `current_plan` | 이전 응답의 `plan`입니다. 일정 수정 요청에 사용합니다. |

선택 조건은 다음과 같습니다.

| 구분 | API 필드 |
|---|---|
| 출발지 | `departure`, `departure_latitude`, `departure_longitude`. 좌표는 둘 다 보내거나 둘 다 비웁니다. |
| 여행 기간 | `start_date`, `trip_days`. 프론트에서 선택한 두 날짜로 일수를 계산하며, 일수는 1 이상의 정수입니다. |
| 이동 조건 | `transport`: `driving`·`walking`·`transit`, `mobility_aid`: `wheelchair`·`stroller`·`none` |
| 취향·필요 시설 | `travel_styles`, `requirements` |
| 귀환 | `return_to_origin`. 선택 UI는 제거했으며 자연어 요청과 기존 데이터 처리를 위해 유지합니다. |
| 숙소 상태 | `lodging_status`: `undecided`(미정), `provided`(숙소 정보 제공), `not_needed`(숙박 불필요), 미입력은 `null` |
| 숙박일별 숙소 | `lodging_stays`: `night`, `name`, `address`, `latitude`, `longitude`, 선택적인 `provider_place_id`·`place_url` 목록 |

미선택 값은 `null` 또는 빈 배열로 표현합니다.

`night=N`은 N일차 관광 후의 숙소이며 1 이상, `trip_days` 미만입니다.
같은 숙박일의 선택은 중복될 수 없습니다. 숙소 이름은 1~200자,
주소는 최대 300자이며 좌표는 제주 검색 범위의 유한한 수입니다.
숙소가 선택되어 있으면 상태는 `undecided` 또는 `provided`여야 합니다.
`undecided`에는 일부 숙박일만 선택한 경우도 포함합니다.
`provided` 역시 모든 숙박일을 선택했다는 보장은 아니며 비어 있는 숙박일은 미정으로 남깁니다.

Agent가 `changed_options`에 선언하지 않고 숙소 상태·숙박일을 바꾸거나 빠뜨리면 서버가 기대값·실제값을 같은 Agent에 돌려줍니다.
서버가 이전 상태를 대신 채우지 않습니다.
사용자가 아직 숙소를 정하지 않았거나 숙소를 입력하지 않은 경우에도 관광 일정을 먼저 생성하도록 지시합니다.


`travel_styles`의 값은 `자연`, `해변`, `박물관·전시`, `산책로`, `공원`, `시장`입니다.
`requirements`는 `step_free`, `accessible_toilet`, `accessible_parking`입니다.

시작·종료 시각과 휴식 요청은 `message`에 작성합니다.
`/chat`의 선택 조건에는 별도 시간·휴식 필드를 보내지 않습니다.

**대화 응답**

| 응답 필드 | 내용 |
|---|---|
| `reply` | Agent 답변·추가 질문·변경 요약. 서버는 문장을 교체·삭제하거나 안내문을 덧붙이지 않습니다. |
| `options` | 이번 대화까지 반영한 현재 조건 |
| `plan` | 생성·수정한 전체 일정. 질문이나 일반 답변이면 `null` |
| `map_routes` | 최종 일정에 연결되고 검증된 지도 경로 목록 |
| `transit_routes` | 이번 실행에서 최종 버스 이동에 연결한 구간별 안내. 경로선 좌표 유무와 별도로 제공합니다. |
| `warnings` | 확인이 필요한 항목과 지도 경로 누락 안내 |
| `restaurant_retry_request` | 기존 일정의 식사 변경 중 검색 서비스 오류나 호출 한도가 발생했을 때 다시 보낼 식사 요청 원문 |
| `meta` | 실행한 시도들의 모델·도구 호출 횟수 합계와 전체 처리시간 |

일정 항목은 방문인 `visit`과 이동인 `move`로 구분합니다.
이동 항목의 `route_id`로 해당 지도 경로와 버스 안내를 연결합니다.
식사를 요청하면 이번 생성 시도의 카카오맵 음식점 조회 결과를 방문 항목으로 넣을 수 있습니다.
식당 이름을 지정하면 이름으로 조회합니다. 주변 식당을 요청하면 일정의 방문지·숙소·출발지 좌표를 기준으로 반경 2km 안의 음식점을 직선거리순으로 최대 5곳 조회합니다. 음식 종류를 지정하면 해당 검색어도 적용합니다.
후보마다 별도의 위치 참조를 발급합니다. 에이전트는 조건에 맞는 한 곳의 앞뒤 이동시간을 확인하고 일정에 맞지 않으면 다른 후보를 검토합니다.
식당 이름·주소·좌표는 조회 결과를 사용하며, 일정표·지도에는 식사 장소로 표시합니다.
필요한 식당 앞뒤 이동의 경로와 좌표를 확인하고, 영업시간과 접근성은 방문 전에 확인하도록 안내합니다.
관광지 DB 검증 표시는 `false`이며 식사 항목에는 `restaurant_address`와 이번 조회의 `restaurant_ref`가 추가됩니다.
다음 요청에는 기존 식당을 이름으로 다시 검색하고 주소가 일치하는지 확인합니다.
식당 검색 결과가 비면 Agent가 기존 일정을 유지하고 다른 식당 이름이나 지역을 묻습니다.
식당 조회가 일시 오류·호출 한도·인증 오류이면 Agent는 `plan=null`로 원인을 안내해야 하며, 일정을 반환하면 서버가 피드백합니다.
일시 오류·호출 한도에는 Agent가 `restaurant_retry_request`에 식사 요청 원문을 넣고, 화면은 ‘식당 검색 다시 시도’ 버튼을 표시합니다.
그 밖의 경우 이 값이 있으면 서버가 피드백합니다. 출발지·숙소 조회 실패는 식당 검색 실패로 처리하지 않습니다.
식사 시각을 지정하면 Agent가 `schedule_changes`의 `start`·`end`(`@meal`)로 기록하고, 서버는 최종 일정의 실제 시각과 대조합니다.
특정 방문 시각의 가능 여부만 묻는 경우 Agent가 `visit_time_check.available`과 답변을 작성합니다.
서버는 저장된 운영시간·휴무 정보로 판정한 값과 다르면 근거와 함께 피드백합니다.

**Agent 응답 검증과 피드백**

Agent는 요청의 의미를 해석해 다음 내부 필드로 선언합니다. 서버는 사용자 문장을 정규식이나 특정 단어로 다시 해석하지 않습니다.
별도 의도 분류 호출 없이 기존 단일 Agent가 도구를 사용해 응답합니다.

| 내부 필드 | 의미 | 서버 검사 |
|---|---|---|
| `changed_options` | 이번 대화에서 새로 정하거나 바꾼 `options` 필드 | 선언하지 않은 필드가 현재 값과 다르면 피드백. 빈 값도 선언 없이 채우지 않음 |
| `schedule_changes` | 방문 추가·삭제·일차 이동, 시각·체류·휴식 조건 | 원문 근거 존재, 일차 범위, 대상 존재, 조건 충돌, 최종 일정의 실제 값 |
| `visit_orders` | 사용자가 정한 방문 순서 | 원문 근거, 중복 장소, 최종 일정의 실제 순서 |
| `needs_clarification` | 확인 질문 여부 | 확정 일정과 동시에 반환하면 피드백 |
| `period_confirmed` | 당일 여행 기간 연장의 명시·동의 | 당일에서 늘렸는데 없으면 피드백 |
| `accessibility_checks.findings` | 시설 문의 답변에 쓴 Y·N·unknown | DB 집계·시설 원문으로 판정한 값과 대조 |
| `visit_time_check.available` | 방문 가능 여부 | 휴무·개장·입장 마감·폐장·자정 경계로 판정한 값과 대조 |
| `restaurant_retry_request` | 식당 조회 일시 오류 때 다시 보낼 원문 | 마지막 식당 조회 상태와 원문 존재 |

검증 실패는 기대값·실제값을 담아 같은 Agent에 최대 1회 돌려줍니다. 응답 형식 오류도 같은 경로로 돌려줍니다.
일정·정보 검증에서 실패하면 첫 해석의 조건을 고정합니다. 재시도는 조건을 빼거나 바꿀 수 없고, 근거 있는 조건 추가만 할 수 있습니다.
위치 근거가 없는 숙박일만 다시 확인 대상으로 풀며 나머지 숙박일과 교통·접근성 조건은 고정합니다.
재시도 응답이 확인 질문이면 조건을 적용하지 않으므로 고정 조건 비교를 생략합니다.
DB·외부 API·인증·취소·시간 초과는 Agent 피드백 대상이 아니며 각각의 오류로 응답합니다.

`transport`에는 일반 이동수단명만 작성하도록 지시합니다.
예외적으로 `버스 102번(승차·하차 설명)`처럼 노선 번호가 붙은 표기는
ScheduleItem 입력에서 `버스`로 정리하며, 중첩된 정류장 이름의 괄호도 처리합니다.
모호한 복합 이동수단과 불완전한 설명은 임의로 해석하지 않습니다.
경로 ID·조회 수단·이동시간 대조는 기존 기준으로 계속 적용합니다.

일정의 시간 형식·겹침·소요시간과 요청한 일차의 수·순서를 검증합니다.
새 일정의 이동 항목은 이번 Agent 실행의 조회 기록과 추가로 대조합니다.

| 검증 항목 | 기준 |
|---|---|
| 경로 ID | 이번 시도의 고유한 경로 ID를 사용합니다. 누락·미등록 ID는 아래 조건에서만 보완하며 중복 ID와 여러 이동에서 재사용한 ID는 거부합니다. |
| 이동수단 | 일정 표기와 조회 기록이 일치해야 합니다. 이번 일정에서 확정한 이동수단이 도보면 도보만, 자동차면 자동차·도보, 대중교통이면 대중교통·도보를 허용합니다. |
| 이동시간 | 조회 결과의 초 단위를 분으로 올림한 값과 비교하며 ±1분을 허용합니다. |
| 상세 근거 | 최종 방문마다 같은 시도의 성공한 상세 조회가 있어야 합니다. 요청·응답의 장소 ID가 같아야 하며 이전 시도의 조회로 대신하지 않습니다. |
| 순서 비교 경계 | 하루 전체 비교를 수행했다면 최종 출발지·선택 숙소·귀환 조건과 맞는 성공 근거가 있어야 합니다. 제안 순서의 강제 채택 검사는 아닙니다. |

누락·미등록 경로 ID의 보완에는 이번 시도의 검색·상세 조회에서 확인한 방문 좌표를 사용합니다.
양 끝점·방향·이동수단·시간이 맞는 미사용 경로가 하나일 때만 ID를 연결합니다.
이미 조회 기록에 존재하는 ID는 덮어쓰지 않으며, 모호한 후보·알 수 없는 경계는 보완하지 않습니다.
보완은 시간표·방문 장소·조건을 바꾸지 않고 후속 검증을 그대로 적용합니다.

각 시도에서 이 검증은 장소 DB 조회 전에 실행합니다.
첫 검증 실패에는 아래 자동 재생성 규칙을 적용하며,
최종 실패하면 HTTP 502 `plan_validation_failed`를 반환합니다.
오류 응답은 `error.code`, `error.message`, `error.details` 구조입니다.
응답 형식 자체가 맞지 않으면 HTTP 502 `llm_invalid_response`를 반환하며 일정 검증의 재생성과 구분합니다.
서버는 `CHAT_SCHEMA_ERROR`에 발생 단계·오류 종류·실패 필드와 사유를 기록합니다.
진단 로그에는 입력 원문이나 AI 응답 전체를 기록하지 않습니다.

실패한 새 일정은 반환하지 않으며, 화면은 이전에 받은 일정을 유지합니다.
질문 응답과 이전 저장 일정의 입력에는 새 이동 검증을 적용하지 않습니다.
후속 요청으로 전체 일정을 다시 생성하면 새 결과의 모든 이동을 검증합니다.

**장소명 검색과 누락 ID 보완**

Agent는 주변 추천에 `search_places`,
특정 장소 이름 조회에 `search_places_by_name`을 사용합니다.
이름 검색은 기본 5개, 최대 10개의 후보를 반환합니다.

공백·대소문자·한글 유니코드 표기를 정규화한 이름 일치는 `exact`,
이름 일부가 겹치는 후보는 `partial`로 구분합니다.
부분 일치나 동명 후보를 이름만으로 같은 장소라고 확정하지 않습니다.

`/chat`에서는 시간·일차·이동 검증 이후 누락된 방문 장소 ID를 보완합니다.

| 조건 | 처리 |
|---|---|
| 이번 실행에서 검색과 상세 조회를 모두 성공함 | 보완 근거로 사용합니다. 상세 조회의 요청 ID와 응답 ID도 같아야 합니다. |
| 일정 이름과 상세 조회 이름이 정규화 후 일치하고, DB에서도 같은 이름의 후보가 하나임 | 누락된 `place_id`를 보완합니다. |
| 부분 일치·동명 후보·근거 부족 | ID를 임의로 채우지 않고 기존 미확인 안내를 유지합니다. |
| 기존 ID가 있음 | 보완으로 덮어쓰지 않고 기존 DB 검증을 적용합니다. |
| 보완에 필요한 DB 조회 실패 | HTTP 500 `internal_error`를 반환합니다. |

질문 응답에는 ID 보완을 적용하지 않습니다.
이전 대화와 저장된 일정은 이번 실행의 조회 근거로 사용하지 않습니다.
보완된 ID를 포함해 각 방문일의 휴무 여부를 검사합니다.
휴무일 방문이 있으면 해당 시도의 검증을 실패로 처리합니다.

각 방문일의 달에 맞는 운영시간에서 다음 조건을 검사합니다.

| 조건 | 검증 실패 기준 |
|---|---|
| 개장 | 방문 시작이 개장 시각보다 빠름 |
| 입장 마감 | 입장 마감이 있으며 방문 시작이 그 시각보다 늦음 |
| 폐장 | 방문 종료가 폐장 시각보다 늦음 |

개장·입장 마감·폐장 정각은 허용합니다.
한 방문에 위반이 여러 개 있으면 재생성에서 함께 수정하도록 모두 전달합니다.
입장 마감이 없는 경우에는 시각을 만들어 넣지 않습니다.

`find_opening_hours`는 해당 월의 첫 유효 구간을 읽습니다.
빈 값·잘못된 값·해당 월 정보 없음은 추정하지 않으며, 상시 개방은 시간 제약 검사를 생략합니다.
폐장 값 `24:00`은 당일 끝으로 해석하지만, 날짜를 넘기는 야간 운영은 해석하지 않습니다.
기존 `find_closing_time`의 반환 형식은 유지합니다.

자동 재생성 후에도 검증에 실패하면 HTTP 502 `plan_validation_failed`를 반환합니다.
이 검사를 통과하면 기존 DB 검증으로 장소명과 좌표를 확정합니다.
시간·일차·이동 검증에 실패하면 ID 보완과 휴무일·운영시간 DB 조회는 수행하지 않습니다.

두 Agent 모두 이름 검색을 지원하지만,
누락 ID의 서버 보완은 `/chat`에만 적용했습니다.

평가의 H5는 두 검색 도구의 결과를 모두 검색 근거로 인정합니다.
평가 스크립트는 Agent 원본 응답을 평가하므로,
`/chat`에서 ID를 보완한 뒤의 응답과 평가 결과가 다를 수 있습니다.

**경로 출발·도착 좌표 검증**

`/chat`은 DB에서 방문 장소의 이름과 좌표를 확정한 뒤,
지도 경로를 응답에 넣기 전에 `validate_route_endpoints`를 실행합니다.

| 검증 대상 | 기준 |
|---|---|
| 방문 장소 앞뒤의 이동 | `verified: true`인 방문 장소의 DB 좌표와 해당 이동의 요청 좌표를 대조합니다. |
| 연속 이동 | 직전 이동의 도착 좌표와 다음 이동의 출발 좌표를 대조합니다. |
| 최초 출발 | 유효한 출발지 좌표가 있으면 1일차 첫 이동의 출발 좌표와 대조합니다. |
| 최종 귀환 | 출발지 귀환 조건이 true이고 좌표가 있으면 마지막 일차의 마지막 이동 도착 좌표와 대조합니다. |
| 선택한 숙소 | N번째 숙박일의 위치를 N일차 마지막 이동의 도착과 N+1일차 첫 이동의 출발 좌표에 대조합니다. |

출발 위치와 첫 방문지, 연속한 방문지, 마지막 방문지와 요청한 귀환지·선택 숙소가 서로 다른 위치이면 그 사이의 이동 항목을 확인합니다.
위도와 경도 차이가 각각 0.000001도 이내인 같은 위치에서는 이동 항목을 생략할 수 있습니다.
숙소가 미정인 구간은 건너뛰고, 숙박 불필요로 매일 원래 출발지에서 출발하는 일정은 출발과 요청한 귀환을 일차별로 검사합니다.
이미 조회한 경로의 끝점과 방문지를 대조할 때는 직선거리 100m 이내를 허용합니다.
비교에는 길찾기에 전달한 좌표를 사용하며 도로선 `paths`는 사용하지 않습니다.
확인되지 않은 방문 장소나 기준 좌표가 없는 끝점은 검사에서 제외합니다.
여러 날의 일정을 매일 같은 출발지에서 시작한다고 가정하지 않습니다.

불일치하거나 비교할 경로 좌표가 잘못되면 해당 시도의 검증을 실패로 처리합니다.
자동 재생성 후에도 검증에 실패하면 HTTP 502 `plan_validation_failed`를 반환합니다.
실패한 새 일정과 지도 경로는 반환하지 않으며, 화면은 이전 결과를 유지합니다.

질문 응답과 기존 저장 일정의 입력에는 적용하지 않습니다.
후속 요청으로 생성한 새 일정은 다시 검사합니다.
기존 `/plan`에는 이번 좌표 검증을 적용하지 않았습니다.

**필수 접근 조건 검증**

`/chat`은 장소 DB 확인과 경로 끝점 검증 이후 접근 조건을 검사합니다.
`plan_accessibility.py`는 서버가 직접 조회한 장소 상세 정보를 사용하며,
AI가 생성한 시설 값이나 기존 일정의 설명을 판정 근거로 사용하지 않습니다.

Agent 도구 `get_place_details`는 `accessibility`에 장애인 화장실·주차구역과
계단·경사 집계 값을 제공합니다. 시설 유무는 집계 값과 `기본정보`의
명시적인 장애인 화장실·주차장 유무 원문을 함께 대조합니다.
주변·추천 화장실을 해당 장소의 시설로 간주하지 않습니다.

| 판정 | 처리 |
|---|---|
| 필수 시설 없음(N) | 해당 일정의 검증을 실패로 처리하고 최대 한 번 재생성합니다. |
| 시설 존재 근거 있음(Y) | 해당 시설 유무 조건을 통과시킵니다. 전체 동선의 이용 가능성을 보장하지 않습니다. |
| 미확인·정보 충돌·장소 미확인 | 시설 없음으로 단정하지 않고 `warnings`에 조건 미확인과 방문 전 확인 안내를 추가합니다. |

현재 계단 없는 방문 동선과 휠체어·유모차 전체 동선 이용 가능 여부는
집계 값만으로 확정하지 않으며 미확인으로 안내합니다.
`has_slope_or_stairs`의 Y만으로 계단 존재를, N만으로 선택한 동선의 계단 부재를 단정하지 않습니다.

첫 일정 응답에서는 사용자가 선택한 필수 조건과 보조기구를 유지합니다.
조건 변경을 확인하는 질문 응답은 기존 흐름대로 허용합니다.
재생성에서는 고정된 조건을 임의로 완화할 수 없습니다.

같은 시도의 중복 장소는 한 번 조회하고, 재생성 시에는 다시 조회합니다.
일반 정보 질문은 기존 여행 조건과 일정표를 유지합니다. 사용자가 새로 지정·변경한 조건이 있으면 해당 항목만 반영합니다.
특정 장소의 시설·접근성을 문의하면 서버가 정확한 장소명으로 조사 DB를 확인하고, 같은 시도의 상세 조회가 있으면 재사용합니다.
화장실·주차구역의 기본정보와 지점별 현장 기록을 구분해 안내합니다. 장소가 모호하면 이름을 묻고, 자료가 없거나 충돌하면 미확인으로 표시합니다.
시설 문의와 무관한 일반 질문은 추가 접근성 조회 없이 처리합니다.
DB 오류나 잘못된 조회 응답은 HTTP 500 `internal_error`로 처리하며 재생성하지 않습니다.
기존 `/plan`에는 이 서버 검증을 적용하지 않았습니다.

**검증 실패 후 자동 재생성**

`/chat`은 최초 생성 후 일정 검증에 실패하면 최대 한 번 다시 생성합니다.
Agent 실행은 총 두 번까지이며, 한 실행 안의 모델 호출은 여러 번일 수 있습니다.

일정을 부분 수정할 때 서버는 직전 일정표에 실제로 들어 있는 방문지·방문일·방문 횟수·체류시간과 새 일정표를 대조합니다.
예를 들어 “해변만 45분으로 바꾸고 수목원은 그대로”라면 해변은 45분, 수목원은 직전 일정의 실제 체류시간이어야 합니다.
앞선 방문이 길어지면서 수목원 도착 시각은 늦어질 수 있습니다. 도착 시각까지 고정한 경우에는 시각도 검사합니다.
“오후 1시 이후에만 여행”은 첫 출발을 포함하고, “수목원 체류를 15분 줄여”는 직전 수목원 체류시간에서 15분을 뺍니다.
장소나 적용일을 특정할 수 없거나 ‘유지’라고 한 수치가 기존 값과 다른 경우에는 확인 질문을 반환합니다.

서버가 확인한 시간 조건은 응답의 `plan.schedule_limits`에 담겨 다음 요청의 `current_plan`으로 전달됩니다.
이 필드가 없는 예전 일정은 저장된 방문일과 체류시간을 기준으로 삼습니다. 과거에 어느 시각을 고정했는지는 복원할 수 없습니다.
채팅에 표시하는 방문 시각과 체류시간도 검증을 마친 일정표에서 읽습니다.
출발 날짜·기간·이동수단을 입력값에서 확인할 수 없으면 필요한 항목을 되묻습니다.
예를 들어 사용자가 ‘이동수단만 도보로’라고 하면 조건 화면과 안내 문구가 함께 도보로 바뀝니다.

| 상황 | 처리 |
|---|---|
| 시간·일차·경로 ID·이동수단·이동시간·휴무일·운영시간·경로 좌표·필수 시설 검증 실패 | 첫 실패 이유를 전달해 최대 한 번 전체 일정을 재생성합니다. |
| 재생성 결과가 다시 검증에 실패하거나 고정된 조건을 변경함 | 추가 재생성 없이 HTTP 502 `plan_validation_failed`를 반환합니다. 조건 변경의 오류 상세 필드는 `options`입니다. |
| 입력·DB·외부 서비스 오류 또는 AI 응답 형식 오류 | 자동 일정 재생성 없이 기존 오류 처리를 적용합니다. |
| 질문 응답·필수 정보 부족·검증을 통과한 빈 일차 | 자동 재생성 대상이 아닙니다. |

재생성 요청은 원래 메시지·대화 기록·선택 옵션·기존 일정을 유지한 채
마지막 사용자 JSON에 `plan_retry`를 추가합니다.
`locked_options`는 재생성 결과와 대조할 여행 조건입니다. 최초 초안의 값이 기존 선택이나 이번 요청에서 확인한 변경값과 다르면 입력에서 확인한 값을 사용합니다.
출발지와 좌표·날짜·기간·이동수단·보조기구·여행 종류·필수 조건·귀환·확인된 숙소 선택을 유지합니다.
여행 종류·필수 조건 목록과 숙박일별 숙소 목록의 순서만 다른 경우는 허용합니다.
첫 시도의 숙소 선택 근거가 거절되면 해당 숙박일만 `lodging_recheck_nights`로 지정하고 숙소 상태의 고정을 해제합니다.
해당 숙박일은 원래 선택을 유지하거나 이번 시도의 새 조회로 다시 확인하며, 미확인이면 원래 선택을 유지한 질문을 반환할 수 있습니다.
그 밖의 숙박일과 여행 조건은 계속 고정하고 최종 숙소 선택 근거를 다시 검사합니다.

실패한 일정에서는 경로 ID와 DB 확인 표시·좌표를 제거해 참고 자료로만 전달합니다.
장소와 이동은 이번 실행에서 다시 확인하도록 지시하며,
첫 시도의 경로 기록과 도구 응답을 두 번째 시도의 검증 근거로 합치지 않습니다.
오류 피드백은 최대 20개이며 각 이유는 500자까지 전달합니다.
시간표 차이와 표기 소요시간이 다르면 현재 시각·소요시간과 당일 범위의 계산 근거를 함께 전달합니다.
예를 들어 11:27~11:50에 24분을 적었다면 ‘11:27 + 24분 = 11:51’을 참고로 제시합니다.
사용자 고정 시각과 이번 조회값을 지켜 다시 계산하도록 하며 서버가 시간표를 자동 수정하지는 않습니다.

재생성 결과도 동일한 전체 검증을 통과해야 합니다.
조건을 유지한 질문 응답은 `plan: null`로 반환할 수 있습니다.
유효한 새 일정이 없으면 화면은 이전 결과를 유지합니다.

정상 응답의 `meta`에는 응답을 받은 각 시도의 모델·도구 호출 횟수를 합산하고,
`elapsed_seconds`에는 전체 처리시간을 기록합니다.
외부 통신 재시도는 기존 모델 설정을 따르며, 자동 일정 재생성과 구분합니다.
이 기능은 `/chat`에 적용하며 기존 `/plan`과 Agent 직접 평가 실행에는 적용하지 않습니다.

**요청 시간 제한과 취소**

| 구분 | 동작 |
|---|---|
| 서버 전체 제한 | 요청 실행 등록부터 최초 생성·검증·최대 1회 재생성까지 하나의 150초 예산을 사용합니다. 재생성에서 시간을 초기화하지 않습니다. |
| 프론트 대기 제한 | 180초가 지나면 `client_timeout`으로 대기를 끝내고 서버에 취소를 통지합니다. 서버의 150초 초과 오류는 `request_timeout`으로 구분합니다. |
| 사용자 취소 | 생성 요청을 중단하고 별도 신호로 취소 API를 호출합니다. 취소 통지는 최대 5초 동안 시도하며, 실패해도 화면의 취소 상태를 오류로 바꾸지 않습니다. |
| 후속 호출 차단 | 모델의 실제 HTTP 전송과 SDK 재시도, 도구 실행·외부 요청 전후에 상태를 확인합니다. 취소·시간 초과를 확인한 뒤에는 후속 호출과 결과 반영을 막습니다. |

브라우저는 `POST /api/chat/cancel`, 백엔드는 `POST /chat/cancel`을 사용합니다.
생성 요청의 헤더에 넣었던 식별자를 본문에 전달합니다.

```json
{"request_id": "aaaaaaaa-aaaa-4aaa-8aaa-aaaaaaaaaaaa"}
```

정상 취소 응답은 같은 `request_id`와 `state`를 반환합니다.
`state`는 `cancelled`, `timed_out`, `completed` 중 하나이며,
이미 완료되거나 시간 초과된 요청은 뒤늦은 취소로 상태를 바꾸지 않습니다.
취소가 생성 요청보다 먼저 도착하면 해당 식별자를 취소 상태로 보관해 실행을 막습니다.

| HTTP | 오류 코드 | 의미 |
|---|---|---|
| 400 | `invalid_request` | 요청 본문 또는 식별자 형식이 잘못됐습니다. |
| 409 | `request_cancelled` | 취소된 요청입니다. |
| 409 | `request_conflict` | 사용 중이거나 보관 중인 식별자를 재사용했습니다. 취소 상태의 식별자는 `request_cancelled`로 처리합니다. |
| 409 | `request_finished` | 이미 처리가 끝난 요청입니다. |
| 503 | `chat_busy` | 실행 작업 또는 요청 기록의 한도에 도달했습니다. |
| 504 | `request_timeout` | 서버의 전체 150초 예산을 초과했습니다. |

기존 외부 서비스 오류와 `llm_timeout`의 구분은 유지합니다.
취소 통지는 전달을 보장하지 않으며, 서버는 연결 종료도 감지해 중단 상태를 기록합니다.
이미 진행 중인 외부 통신을 강제로 종료하는 방식은 아니므로 취소 응답 후에도 작업이 남을 수 있습니다.
늦게 도착한 결과는 버리고, 실제 작업이 끝날 때까지 실행 슬롯을 유지합니다.

실행 작업은 프로세스당 최대 4개이며, 초과 요청은 대기열에 쌓지 않고 거부합니다.
활성 작업과 최근 식별자 기록을 합쳐 최대 1,024개를 보관하며, 최근 기록은 300초 후 만료됩니다.
취소 상태는 프로세스 메모리에 있으므로 현재 구성은 단일 Uvicorn worker를 기준으로 합니다.
여러 worker·서버 사이의 취소 상태 공유는 구현하지 않았습니다.

**버스 승하차 안내**

`transit_routes`는 `route_id`, `requested_at`, `segments`를 제공합니다.
`segments`는 선택된 전체 경로의 버스·도보·미확인 구간 순서를 유지합니다.

| 구간 필드 | 내용 |
|---|---|
| `type` | `BUS`, `WALKING`, `UNKNOWN` |
| `distance_m`, `duration_seconds` | 확인된 구간 거리와 소요시간. 없거나 잘못된 값은 `null` |
| `route_numbers` | 같은 버스 구간에서 이용 가능한 노선 목록. 화면에서는 '또는'으로 구분 |
| `boarding_stop`, `alighting_stop` | 승차·하차 정류장명. 미확인은 `null` |
| `ride_stop_count` | 승차지는 제외하고 하차지는 포함한 이동 정거장 수. 미확인은 `null` |

정거장 수는 [카카오 대중교통 경로 응답](https://developers.kakao.com/docs/ko/kakaomap/rest-api)의
정류장 목록을 사용합니다. 승하차 이름과 목록의 양 끝이 일치하고
유효한 이름이 2개 이상이면 목록 길이에서 1을 뺍니다.
이름이 같은 정류장도 목록의 각 위치를 유지합니다.
빈 목록·잘못된 이름·승하차 불일치는 정거장 수를 추정하지 않습니다.

Agent용 버스 요약과 화면용 안내는 같은 `ride_stop_count` 계산을 사용합니다.
승차지를 포함한 목록 길이인 `stop_count`는 Agent 요약에서 제외합니다.
실시간 도착 차량의 `remaining_stops`는 승차 정류장까지 남은 정류장 수이며 별도 값입니다.

버스 지도 도구가 이미 선택한 경로에서 안내를 기록하므로,
이 정보를 만들기 위해 외부 API나 AI를 추가 호출하지 않습니다.
최종 일정에서 사용하는 유일한 경로 ID와 이동수단이 일치하는 기록만 노출합니다.
첫 실패 후 재생성하면 두 번째 실행의 기록만 사용합니다.
지도 좌표가 없어도 안내는 제공하며, 이전 저장 일정에 안내가 없으면 미확인으로 표시합니다.

**주변 숙소 검색과 선택**

관광 일정을 생성한 뒤 숙박일별 일정표 위의 '주변 숙소 보기'를 누릅니다.
그날 마지막 방문지가 DB로 확인되고 좌표가 있을 때 반경 5km 안의 후보를 최대 5개 조회합니다.
마지막 방문지가 미확인이면 앞선 관광지나 원래 출발지를 임의의 검색 기준으로 대신하지 않습니다.
마지막 여행일과 숙박 불필요 상태에는 숙소 선택 영역을 표시하지 않습니다.

후보는 기존 관광지 DB와 구분한 [카카오 로컬 숙박 분류(AD5) 검색](https://developers.kakao.com/docs/ko/local/dev-guide)을 사용합니다.
AI 추가 호출 없이 목록을 조회하고, 사용자가 선택하면 위치를 선택 옵션에 넣어 후속 대화 요청을 보냅니다.
숙소 검색 식별값을 관광지 DB의 `place_id`로 사용하거나 숙소를 관광지 `visit`으로 만들지 않습니다.

| API | 내용 |
|---|---|
| 백엔드·프록시 주소 | `GET /lodgings/nearby`, 브라우저는 `GET /api/lodgings/nearby` |
| 필수 검색 위치 | `latitude`: 33.10~33.60, `longitude`: 126.08~127.00 |
| 검색 범위·개수 | `radius_m`: 1~20,000m, 기본 5,000. `max_count`: 1~10, 기본 5 |
| 응답 공통 정보 | `source: kakao_local`, 시간대가 있는 `requested_at`, 요청과 같은 `center`·`radius_m`, `places` |
| 후보 항목 | `provider_place_id`, `name`, `address`, `phone`, `latitude`, `longitude`, `distance_m`, `place_url` |
| 후보 없음 | HTTP 200과 빈 `places`를 반환하며 검색 위치와 조회 시각은 유지합니다. |
| 오류 | 입력 400 `invalid_request`, 한도 초과 429 `lodging_search_rate_limited`, 설정·인증 503 `lodging_search_unavailable`, 검색·응답 502 `lodging_search_failed` |

`distance_m`는 기준 좌표에서 후보까지의 직선거리이며 도로 이동 거리가 아닙니다.
지도 링크는 후보 식별값과 일치하는 `https://place.map.kakao.com/` 주소만 허용합니다.
검색 중복·제주 범위 밖 좌표·숙박 이외 분류·반경 밖 후보는 제외합니다.
API 키와 내부 필드는 응답에 넣지 않으며 가격·잔여 객실·접근성을 확인한 값으로 만들어 넣지 않습니다.

서버의 숙소 검색 통신 제한은 20초, 프론트 대기시간은 25초입니다.
날짜 전환 등으로 조회 영역이 사라지면 프론트 요청을 취소하고 늦게 도착한 결과를 적용하지 않습니다.
검색 실패는 기존 관광 일정과 지도를 유지한 채 안내하며 재조회할 수 있습니다.

선택은 예약이 아니라 일정의 기준 위치를 지정하는 동작입니다.
사용자가 입력한 선택 또는 현재 메시지에서 이름·주소로 지목하고 이번 실행의 `find_location`으로 확인한 위치만 새 숙소 근거로 인정합니다.
이전부터 선택한 동일 숙박일의 숙소는 유지할 수 있으며, 새 숙소를 AI가 임의로 선택하는 것은 거부합니다.
위치 조회 근거와 좌표를 비교할 때 소수점 반올림에 따른 0.000001도 이내의 차이만 허용합니다.

| 상황 | 위치 처리 |
|---|---|
| 현재 요청에 선택된 숙소가 있고 이름·주소가 일치함 | 요청별 도구가 선택 좌표를 반환합니다. `source: selected_lodging`·`lookup_performed: false`로 구분하며 외부 위치 검색을 하지 않습니다. |
| 다른 숙소 또는 위치 정정을 요청함 | 새 위치를 조회합니다. 선택 숙소용 도구의 `refresh: true`로 동일 검색어도 다시 조회할 수 있습니다. |
| 새 숙소 선택 근거를 검사함 | 선택 좌표를 재사용한 응답은 새 숙소나 다른 숙박일의 조회 근거로 인정하지 않습니다. |
| 지역명만 생략한 숙소명을 요청함 | `신라호텔 → 제주신라호텔`처럼 알려진 제주 행정구역 접두사만 생략한 구체적 이름을 제한적으로 허용합니다. 이번 조회 키워드와 실제 반환 이름·좌표가 일치해야 합니다. |

이름 재사용은 현재 요청의 `options.lodging_stays`만 사용하며 이전 대화나 실패 일정에서 가져오지 않습니다.
동명 선택의 위치가 서로 다르면 재사용하지 않습니다. 일반 명칭·일부 상호·다른 지역 상호를 별칭으로 추정하지 않습니다.
좌표 재사용을 숙소 영업·가격·객실·접근성의 별도 확인으로 설명하지 않습니다.

숙소가 없는 일차의 첫·마지막 이동 때문에 관광 일정 전체를 거부하지 않습니다.
서버는 숙소 미정일 때 첫 관광지 앞의 이동과 마지막 관광지 뒤의 이동만 제외한 뒤
남은 일정의 시간·경로 ID·이동수단·이동시간·휴무일·운영시간·끝점을 검증합니다.
최초 여행 출발, 마지막 날 최종 이동, 관광지 사이 이동과 선택한 숙소 이동은 제외하지 않습니다.
방문이 없는 일차는 임의 정리하지 않으며, 원래 입력과 방문 시각·체류시간은 변경하지 않습니다.
제외한 이동은 지도 경로·버스 안내에도 노출하지 않고 답변·확인사항·전제에 제외 사실과 시간 재계산 필요를 표시합니다.

숙소를 선택하거나 취소하면 기존 관광 조건을 포함해 전체 일정을 다시 요청합니다.
새 일정이 실패하면 이전 지도·일정은 유지하고 선택 옵션과 재전송 요청을 남깁니다.
지도에는 전날 숙소의 출발, 당일 숙소의 도착, 마지막 날 원래 출발지 귀환을 구분합니다.
숙소가 미정인 둘째 날 이후에 원래 출발지를 자동으로 숙소 출발점처럼 표시하지 않습니다.

**장소 상세 API**

백엔드는 `GET /places/{place_id}/details`,
브라우저는 `GET /api/places/{place_id}/details`를 사용합니다.
장소 ID는 공백 제거 후 1~80자입니다. 기존 DB 조회 도구를 사용하며 AI는 호출하지 않습니다.

| 응답 필드 | 내용 |
|---|---|
| `place_id`, `name` | 확인한 장소 ID와 DB 이름 |
| `category` | 장소 분류. 미등록은 `null` |
| `closed_days` | 등록된 휴무 정보 또는 '확인 안 됨' |
| `spots` | 지점 이름 `name`과 접근 동선 설명 `description` |
| `accessibility_facts` | 조사 원문의 `section`, `facility_name`, `description`, `raw_value` |

다른 장소 ID나 잘못된 성공 응답은 정상 결과로 전달하지 않습니다.
입력 오류는 400 `invalid_request`, 없는 장소는 404 `place_not_found`,
DB·응답 오류는 500 `internal_error`입니다.
서버의 파일 경로나 응답 모델 밖의 내부 필드는 포함하지 않습니다.

**상세 창과 일정표**

일정표는 시간·일정·소요시간 세 칸으로 표시합니다.
방문별 `accessibility_notes`는 장소 상세 창의 '이번 일정의 접근성 안내'에 표시합니다.
같은 장소를 여러 번 방문해도 클릭한 방문 항목의 메모만 전달합니다.
이 메모는 일정 생성 시 작성된 안내이며 아래의 조사 원문과 구분합니다.
상세 조회가 실패하거나 자료 연결이 미확인이어도 기존 메모를 표시합니다.
이동 항목의 메모는 일정표에서 '이동 시 확인사항'을 펼쳐 확인합니다.

시설·추천 원문은 조사 분류와 시설명이 모두 같은 항목끼리 묶습니다.
시설명이 다른 주차장이나 화장실의 내용을 합치지 않으며,
빈 이름은 미등록으로 안내하고 추천 기호를 등급으로 바꾸지 않습니다.
'미설치'라는 조사 원문과 표시할 자료가 없는 상태를 구분합니다.
지점별 설명은 각 지점 이름을 펼쳐 읽습니다.

'시설·동선 정보'와 '사진' 버튼으로 보기를 전환합니다.
두 조회는 독립적으로 실행하고, 각각 재시도할 수 있습니다.
사진이 없어도 시설 정보를 표시하며, 실패한 한 요청이 다른 결과를 숨기지 않습니다.
각 요청의 대기시간은 15초이며 창을 닫으면 진행 중인 요청을 취소합니다.
닫기 버튼과 Esc로 창을 닫으면 기존 일정·지도와 선택한 일차를 유지하고
장소 버튼으로 초점을 돌려줍니다.

**사진 API**

아래 경로는 백엔드 기준입니다.
브라우저에서는 앞에 `/api`를 붙여 요청합니다.

| 요청 | 응답 |
|---|---|
| `GET /places/{place_id}/images` | 장소 이름과 사용 가능한 사진 목록 |
| `GET /places/{place_id}/images/{image_id}` | 해당 사진 파일 |

사진 목록에는 `image_id`, `url`, `caption`, `alt`를 제공합니다.
CloudFront 사진에는 `photo_id`와 장소별 `contexts`(`spot_name`, `description`, `mapping_confirmed`)를 추가합니다.
프론트는 CloudFront 주소를 직접 사용하고, 기존 파일 API 요청은 해당 주소로 307 이동합니다.
서버의 로컬 파일 경로는 응답에 포함하지 않습니다.

DB에 기록된 장소는 있지만 사진 파일이 없으면 정상 응답으로 빈 목록을 반환합니다.

```json
{
  "place_id": "P001",
  "name": "한림공원",
  "images": []
}
```

장소나 사진이 없으면 404, DB 또는 사진 연결 CSV 조회 오류는 공통 500으로 반환합니다.

사진 조회는 일정 생성과 별도로 실행합니다.
창을 닫으면 진행 중인 목록 요청을 취소하며, 조회 제한 시간은 15초입니다.
사진 조회 오류가 나도 기존 대화·일정·지도는 유지합니다.

**사진 파일 위치와 현재 상태**

`data/processed/place_photos_cloud.csv`가 있으면 통합 WebP 사진을 사용합니다.
장소 연결은 웹용 CSV의 `place_ids` 기준이며 설명은 해당 장소의 `sources` 항목만 표시합니다.
미확인 연결은 ‘장소 연결 미확인’으로 구분합니다.
사진의 시설명·전체 설명과 일치하는 상세 항목은 사진에서 제공하고 시설·동선 보기에서 숨깁니다.
사진 조회 실패·이미지 실패·연결 미확인일 때는 기존 상세 설명을 유지합니다.
중복 설명이 있는 경우 ‘사진 보기’ 링크로 이동할 수 있으며 원본 자료는 변경하지 않습니다.
주소 목록 생성·S3 콘솔 업로드 절차는 [사진 클라우드 연결](place-photo-cloud.md)에 정리했습니다.

주소 목록이 없는 환경에서는 다음 기존 원본 방식으로 동작합니다.

`place_spots`의 `source_file`, `image_file`을 사용합니다.
기록된 CSV와 같은 폴더에 실제로 존재하는 사진만 제공합니다.

예를 들어 다음 기록이라면:

```text
source_file: data/raw/jeju_datahub/hub_1/001-2.csv
image_file: 001_DSC00236.jpg
```

찾는 파일은 다음 위치입니다.

```text
data/raw/jeju_datahub/hub_1/001_DSC00236.jpg
```

원본 폴더 밖의 경로와 지원하지 않는 확장자는 제외합니다.
지원 확장자는 JPG·JPEG·PNG·WEBP·GIF입니다.
원본 사진에는 기존 `data/raw`의 Git 제외 규칙이 적용됩니다.

로컬 통합 WebP는 3,834개이며 Git에서 제외합니다.
사용자는 S3 콘솔 업로드와 CloudFront 표본 사진 표시를 확인했습니다.
한림공원 일정에서 실제 사진·설명 표시와 중복 설명 정리를 사용자에게 확인받았습니다.
원격 파일 전체의 체크섬과 이미지 의미를 전수 검수한 결과는 아닙니다.

## 4. 지도 경로 연결

**처리 흐름**

| 단계 | 처리 |
|---|---|
| 조회 | 자동차·도보·버스 도구가 이동시간과 경로를 조회합니다. |
| 기록 | `backend/app/tools/map_transport.py`에서 조회마다 고유 `route_id`를 만들고 좌표를 이번 요청의 기록에 보관합니다. |
| 일정 연결 | Agent는 도구가 반환한 ID를 해당 `move.route_id`에 넣습니다. 대량의 경로 좌표는 Agent 응답에 넣지 않습니다. |
| 이동 일관성 검증 | `backend/app/services/plan_consistency.py`에서 새 일정의 경로 ID·이동수단·이동시간을 이번 실행의 조회 기록과 대조합니다. |
| 응답 선택 | `backend/app/services/plan_routes.py`에서 최종 일정이 참조한 이번 실행의 경로만 검증해 반환합니다. |
| 화면 표시 | `frontend/src/services/itineraryRoutes.js`에서 선택한 일차의 경로를 고르고, `ItineraryMap.jsx`에서 선으로 표시합니다. |

하나의 경로 ID는 하나의 이동 항목에만 연결합니다.
후속 요청에서는 이전 일정의 ID를 Agent 입력 사본에서 비우고,
유지하는 이동도 이번 실행에서 다시 조회하도록 합니다.
브라우저에 저장된 이전 일정 자체는 변경하지 않습니다.

버스 도구는 환승 횟수가 가장 적고, 같으면 소요시간이 짧은 경로를 선택합니다.
버스 요약과 지도 좌표는 같은 선택 경로를 사용합니다.
지도 좌표를 얻기 위해 카카오 경로를 별도로 재조회하지 않습니다.

버스 도구의 ID는 환승과 도보를 포함한 전체 이동 경로를 가리킵니다.
이 조회 결과는 일정의 이동 항목 하나에 연결하며,
포함된 도보 시간을 다시 더하지 않습니다.

**이동수단별 표시**

| 이동수단 | 좌표 처리 | 표시 |
|---|---|---|
| 자동차 | 도로별 `vertexes`를 좌표 쌍으로 변환하고 도로별 경로를 유지합니다. | 파란 실선 |
| 도보 | 안내 단계별 `path_points`를 별도 경로로 유지합니다. | 초록 점선 |
| 대중교통 | 선택 경로의 버스·도보 단계별 `path.points`를 유지합니다. | 전체 경로를 주황 실선으로 표시합니다. |

경로 좌표는 WGS84의 `[경도, 위도]` 순서입니다.
지도 SDK에는 `LatLng(위도, 경도)` 순서로 전달합니다.
서로 분리된 경로 사이에 임의의 직선을 만들지 않습니다.

지도 경로는 `route_id`, `transport`, `origin`, `destination`,
`distance_m`, `duration_seconds`, `geometry_status`, `paths`, `requested_at`을 제공합니다.

`requested_at`은 서버가 경로 조회를 시작한 시각이며,
제공기관의 갱신 시각과 구분합니다.
지도에는 조회 시각을 한국 시간으로 표시합니다.

사이드바의 일정 지도는 마우스 휠로 확대·축소할 수 있습니다.
사이드바는 위에서부터 일차 선택, 방문지 요약 줄, 지도, 확인할 사항, 숙소, 일정표 순서로 표시합니다.
일정표는 방문 카드와 이동 줄을 세로로 이은 타임라인입니다. 방문 번호는 지도 표시 번호와 같습니다.

일차 선택 버튼은 지도와 일정표 위에 함께 표시합니다.
일차를 변경하면 해당 날짜의 요약 줄·지도·일정표를 함께 전환합니다.
2일 이상 일정에는 일차 버튼 맨 앞에 ‘전체 일정’ 버튼을 둡니다. 누르면 모든 날짜의 일정표를 이어서 보여 주고, 하루 단위인 요약 줄·지도·숙소 선택은 숨기고 안내 문구를 표시합니다. 전체 보기 여부는 저장하지 않아 새로고침하면 일차 보기로 돌아갑니다.
‘전체 경로 보기’는 장소와 경로 전체가 화면에 들어오도록 범위를 조정합니다.
영역 너비가 바뀌면 지도 크기를 다시 계산하면서 중심 위치를 유지합니다.

**좌표 누락과 부분 실패**

| 상황 | 동작 |
|---|---|
| 새 일정의 경로 ID 누락·불일치·중복·재사용 | 새 일정을 반환하지 않고 502 오류를 안내합니다. 화면의 이전 일정은 유지합니다. |
| 새 일정의 이동수단·이동시간이 조회 결과와 불일치 | 새 일정을 반환하지 않고 502 오류를 안내합니다. 화면의 이전 일정은 유지합니다. |
| 일부 구간의 좌표가 잘못됨 | 이동 일관성 검증을 통과한 일정은 유지하고, 확인된 경로만 표시하며 안내합니다. |
| 좌표 없음·좌표 검증 실패 | 이동 일관성 검증을 통과한 일정은 유지하고, 해당 경로선만 제외합니다. |
| 제주버스 실시간 조회 일부 실패 | 확보한 카카오 경로 좌표와 정상 버스 정보를 유지합니다. |
| 이전 저장 일정에 지도 경로가 없음 | 장소와 일정표를 표시하며 경로선을 임의로 만들지 않습니다. |

저상 여부를 알 수 없는 값은 미확인 상태로 유지하며 `False`로 바꾸지 않습니다.
버스 차량의 실시간 위치 마커나 자동 갱신 지도는 구현하지 않았습니다.

## 5. 상태 복원과 영역 너비 조절

추가 질문만 반환되어 `plan`이 `null`이면 기존 지도와 일정을 유지합니다.
새 일정이 반환되면 전체 일정과 연결 경로를 교체합니다.

선택 옵션을 변경하면 다음 메시지에 함께 전달합니다.
그동안 기존 지도·일정은 생성 당시 조건을 기준으로 표시하고,
옵션이 변경된 경우 이전 결과임을 안내합니다.

응답 대기 중에는 메시지 입력과 옵션 변경을 잠그고 ‘요청 취소’ 버튼을 표시합니다.
취소하면 입력을 즉시 다시 활성화하고 기존 일정·지도·옵션·선택 일차를 유지합니다.
취소한 메시지는 실패와 구분하며, 취소하거나 실패한 요청은 사용자가 다시 보낼 수 있습니다.
새 요청 이후 도착한 이전 응답은 적용하지 않으며, 새 여행 시작과 화면 종료 시에도 이전 결과의 반영을 차단합니다.

**대화와 일정**

같은 탭의 `sessionStorage`에 대화·옵션·일정·지도 경로·선택한 일차를 저장합니다.
숙소 미정 상태와 숙박일별 선택도 옵션에 저장하며, 이전 저장 대화에는 숙소 기본 필드를 보완합니다.
새로고침은 저장된 결과를 복원하며,
일정 생성이나 교통 경로 조회를 자동으로 다시 실행하지 않습니다.

응답 대기 중 새로고침한 요청은 실패 상태로 복원해 수동 재전송할 수 있게 합니다.
명시적으로 취소한 메시지는 새로고침 후에도 취소 상태로 복원합니다.
4일 이후의 일차도 저장·복원합니다.
과거 날짜가 포함된 기존 대화를 삭제하지 않으며,
출발일이 지났으면 날짜 재선택을 안내합니다.

‘새 여행 시작’은 대화와 여행 조건·결과를 초기화합니다.
사용자별 서버 대화 저장과 기기 간 동기화는 구현하지 않았습니다.

**사이드바와 너비**

메인 화면은 위쪽 옵션 카드, 아래쪽 대화 카드로 배치합니다.
새 여행에서 채팅 입력창이 비어 있으면 선택한 조건에 맞는 요청 예시를 표시합니다.
예시 버튼을 누르면 버튼에 적힌 문장과 현재 선택한 여행 옵션을 바로 전송합니다.
옵션 카드 오른쪽 위의 ‘옵션 접기’·‘옵션 펼치기’ 버튼으로 옵션을 접습니다. 접어도 선택한 조건과 출발지 검색 상태를 유지합니다.

지도·일정표는 오른쪽에서 열리는 사이드바에 표시합니다.
새 일정이 만들어지거나 바뀌면 사이드바를 자동으로 엽니다. 새로고침으로 복원한 일정에서는 자동으로 열지 않습니다.
헤더의 ‘지도·일정 보기’, 마지막 답변 아래의 ‘지도·일정 열기’ 배너로 열고, ‘접기’ 버튼이나 Esc로 닫습니다.
일정이 없을 때 열면 대화로 일정을 먼저 만들라는 안내와 출발지 지도를 표시합니다.
사이드바가 열리면 제목으로 포커스를 옮기고, 닫으면 열기 전 위치(없으면 헤더 버튼)로 돌려보냅니다.
열림 상태는 저장하지 않으며 ‘새 여행 시작’ 시 닫습니다.

가로 901px 이상에서 사이드바가 열리면 옵션 카드를 숨기고, 대화창만 사이드바 왼쪽 남은 폭과 화면 높이에 맞춰 표시합니다. 입력창은 아래에 붙고 대화 기록만 스크롤하며, 영역 크기가 바뀌어도 최신 메시지를 보여 줍니다. 사이드바를 닫으면 옵션과 대화를 원래대로 표시합니다.
사이드바 왼쪽 경계로 너비를 조절합니다.
기본 너비는 화면의 60%(최대 880px)이며, 최소 420px이고 대화창은 360px보다 좁아지지 않습니다.
메인 화면(옵션·대화)과 헤더의 내용 폭은 최대 1120px입니다.

| 조작 | 동작 |
|---|---|
| 경계 드래그 | 사이드바 너비 조절 |
| Tab으로 경계 선택 후 좌우 방향키 | 너비 조절(왼쪽 = 넓게). Shift를 누르면 더 큰 단위로 이동 |
| Home·End | 최소·최대 너비로 이동 |
| 경계 두 번 클릭 | 기본 너비로 초기화 |

직접 조절한 너비만 비율로 `localStorage`의 `gachi-jeju.workspace-sidebar.v2`에 저장합니다. 두 번 클릭해 기본 너비로 돌리면 저장값을 지웁니다.
저장소를 사용할 수 없어도 현재 화면의 너비 조절은 동작합니다.
가로 900px 이하에서는 사이드바가 전체 화면을 덮고 너비 조절 경계를 숨깁니다.

**첫 방문 가이드 투어**

처음 접속하면 가이드 투어가 자동으로 시작합니다. 설명하는 부분만 밝게 남기고 나머지 화면은 어둡게 덮으며, 카드에 단계·제목·설명과 마스코트를 함께 보여 줍니다(investment-bite 프로젝트의 가이드 방식).
단계는 ① 여행 옵션(옵션 접기 포함) ② 대화 ③ 지도 ④ 일정표가 나올 자리 ⑤ PDF·이메일 ⑥ 사이드바 옆 대화창 순서입니다. 3단계에서 사이드바를 자동으로 열고, 끝나면 시작 전 상태로 되돌립니다.
일정이 없으면 5단계 동안만 누를 수 없는 흐린 PDF·이메일 버튼을 보여 줍니다. 휴대폰 폭에서는 카드를 화면 아래에 고정하고, 6단계 전에 사이드바를 닫습니다.
가이드를 시작하면 스크롤을 맨 위로 올리고, 단계마다 대상의 위쪽 끝이 보이도록 맞춥니다. 가이드 동안 휠 스크롤은 막고, 캐릭터는 화면 밖으로 잘리지 않는 자리로 자동으로 옮깁니다.
끝내거나 건너뛰면 `localStorage`의 `gachi-jeju.guide-tour.v1`에 기록해 다시 자동으로 뜨지 않습니다. 헤더의 ‘가이드 투어’ 버튼으로 언제든 다시 볼 수 있습니다. Esc는 건너뛰기, ←/→는 이전·다음 단계입니다.

화면 디자인 중 상의 없이 정한 내용은 [디자인 적용 결정 목록](design-decisions.md)에 정리했습니다.

## 7. 제약사항과 남은 범위

| 구분 | 현재 범위 |
|---|---|
| 접근성·운영시간 | DB 등록, 경로 존재, 도보 `ACCESSIBLE` 옵션만으로 실제 휠체어 통행을 보장하지 않습니다. 지점별 근거와 미확인 사항을 구분하며, 실제 운영 여부도 별도 확인이 필요합니다. |
| 휴무일 | `get_place_details(visit_dates=...)`가 날짜별 `휴무`·`영업`·`확인 안 됨`을 돌려주고, `/chat`은 휴무일 방문을 `plan_validation_failed`로 막습니다. 2026-11-15 사용자 조사 반영 후 170곳 중 22곳은 휴무일 정보가 없어 항목 메모에 '휴무일 확인 필요'로 남깁니다. 설날·추석·부처님오신날 날짜표는 2026~2028년만 있고, 대체공휴일·임시공휴일은 판정하지 않습니다. |
| 운영시간·관람료 | `/chat`은 개장 전 시작·입장 마감 이후 시작·폐장 이후 종료를 검사하며 정각은 허용합니다. 유효한 운영시간이 없으면 추정하지 않습니다. 날짜를 넘기는 야간 운영은 해석하지 않으며, 시설별 시간·공연 회차·관람료의 상세 조건은 원문 확인이 필요합니다. 기존 `/plan`에는 이번 운영시간 검증을 적용하지 않았습니다. |
| 일정과 교통 정보 대조 | `/chat`의 새 일정은 시간표와 경로 ID·이동수단·이동시간을 검증합니다. DB로 확인된 방문 장소와 길찾기 요청의 출발·도착 좌표도 100m 허용 범위로 대조합니다. 기준 좌표가 없는 끝점은 검사하지 않으며, 도로선 전체의 정확성을 검증하는 기능은 아닙니다. 기존 `/plan`에는 이동 일관성과 좌표 검증을 적용하지 않았습니다. |
| 자동 재생성·대기시간 | 최대 1회 재생성과 검증을 포함해 서버 150초 예산을 공유하며, 프론트는 180초에 대기를 끝냅니다. 취소 이후의 결과 반영과 후속 호출을 차단하지만 이미 진행 중인 외부 통신의 즉시 종료는 보장하지 않습니다. 실제 재시도 후 검증 실패와 경로 ID 오류를 수정한 성공 사례를 모두 관찰했습니다. 반복 성공률과 시간 계산 피드백만의 효과는 확인하지 않았습니다. |
| 버스 상세 안내 | 조회한 경로에 포함된 정보만 제공합니다. 구간·정거장 수가 없으면 미확인으로 표시하며, 이전 저장 일정의 안내를 자동 재조회하지 않습니다. 당일 운행과 실제 승하차 위치는 별도 확인이 필요합니다. |
| 버스 실시간 정보 | 현재 조회된 도착 차량과 저상 여부를 미래 탑승 시점의 정보로 보장하지 않습니다. 정적 정류장 정보가 없는 노선은 제주버스 연동이 제한될 수 있습니다. |
| 장기 일정·숙박 | 입력의 3일 상한은 제거했습니다. 숙소 미정 관광 일정과 숙박일별 숙소 선택을 지원하며 자동차 1박 2일 흐름을 사용자에게 확인받았습니다. 긴 기간 전체의 실제 Agent 생성과 야간 이동은 미검증이며 모델 출력량·응답 시간의 영향을 받습니다. |
| 숙소 추천·예약 | 마지막 방문지 주변의 위치 후보를 제공합니다. 가격·잔여 객실·접근성·예약은 확인하거나 처리하지 않습니다. 다른 지역 검색과 반경·개수 조절은 현재 숙소 화면에 없으며 API에서 반경·개수를 지정할 수 있습니다. |
| 운영 환경 | 현재 검증은 로컬 개발 환경과 단일 Uvicorn worker 기준입니다. 취소 기록과 실행 한도는 프로세스별이며 여러 worker·서버의 공유 저장소는 구현하지 않았습니다. 배포 환경의 API 연결과 사용자별 서버 저장·동기화는 별도 구성 범위입니다. |
| 응답 설명 | 2026-11-19부터 `/chat`은 Agent 답변과 메모를 바꾸지 않고 구조화 값만 검증합니다. 답변 문장과 일정의 불일치, 낡은 숙소 미정 메모는 서버에서 막지 않으며 평가 도구의 설명 검사로만 확인합니다. |
