# 대화형 여행 플래너와 이동 경로 지도

최종 자동 검증일: 2026-11-13
최종 UI 수동 검증일: 2026-11-13
기존 이동 API·경로 지도 수동 검증일: 2026-11-11

자연어 대화와 선택 옵션으로 제주 여행 일정을 생성·수정합니다.
자동차·도보·대중교통 경로와 날짜별 일정표를 함께 표시합니다.

실제 여행지 사진 표시는 원본 파일을 확보한 뒤 추가 검증해야 합니다.

────────────────────────────────────────

## 1. 제공 기능

| 항목 | 동작 |
|---|---|
| 화면 구성 | 왼쪽 여행 옵션, 가운데 대화창, 오른쪽 지도·일정표를 표시합니다. 넓은 화면에서는 경계선을 움직여 영역 너비를 조절합니다. |
| 여행 조건 | 출발지, 출발일·마지막 날, 이동수단, 보조기구, 여행 종류, 필요한 접근 조건을 선택합니다. 옵션 없이 대화로 시작할 수도 있습니다. |
| 대화 | 요청과 선택 옵션을 함께 반영합니다. 정보가 부족하면 질문하고, 후속 요청으로 전체 일정을 수정합니다. |
| 지도·일정표 | 출발지와 방문 장소, 실제 조회한 이동 경로를 표시합니다. 여러 날 일정은 일차별로 전환하며, 확인사항은 일정표 아래에 표시합니다. |
| 장소 상세·사진 | 장소명을 누르면 일정별 접근성 메모, 시설·추천 원문, 지점별 동선 설명과 사진을 확인합니다. 정보·사진은 별도로 조회하며 사진이 없어도 상세 정보를 표시합니다. |
| 버스 탑승 안내 | 이동 행에서 승차 정류장, 버스 노선, 하차 정류장과 이동 정거장 수를 확인합니다. 도보·환승 구간은 순서를 유지합니다. |
| 숙소 미정·선택 | 숙소가 미정이어도 여러 날의 관광 일정을 먼저 만듭니다. 숙박일별 마지막 방문지 주변 후보를 고르면 숙소 전후 이동과 시간을 다시 계산합니다. |

**날짜와 기간**

- 출발일과 마지막 날을 모두 포함해 여행 일수를 계산합니다.
- 같은 날짜는 당일이며, 5일은 4박 5일로 표시합니다.
- 현재 대화형 화면과 `/chat`에는 기존 3일 상한을 적용하지 않습니다.
- 잘못된 날짜, 역순 날짜, 달력 범위를 벗어나는 조합은 거부합니다.
- 달력에서는 한국 시간 기준 오늘보다 이전 날짜를 선택할 수 없습니다.

출발일을 변경하면 선택한 마지막 날을 유지하면서 기간을 다시 계산합니다.
새 출발일이 마지막 날보다 늦으면 마지막 날을 비워 다시 선택하도록 합니다.

시작·종료 시각, 중간 휴식, 여행 마무리는 선택 옵션에서 제외했습니다.
필요하면 자연어로 요청합니다.
귀환 요청 처리를 위해 API의 `return_to_origin` 필드는 유지합니다.

**출발지와 접근성**

기본 출발지는 제주빅데이터센터입니다.
센터 주소 설정값은 `제주특별자치도 제주시 첨단로 241`입니다.

왼쪽 옵션의 ‘출발지 변경’은 지도 없이 검색 입력창과 결과 목록을 표시합니다.
장소를 검색하면 최대 5개의 장소명과 주소를 보여 줍니다.
결과를 누르면 해당 장소의 이름·주소·좌표를 출발지에 반영합니다.
검색어 입력만으로는 출발지가 변경되지 않습니다.

‘센터에서 출발’과 ‘현재 위치 사용’ 버튼은 같은 너비로 나란히 표시합니다.
센터·현재 위치·검색 결과로 출발지를 선택해도 변경 영역은 열린 상태를 유지합니다.
선택 완료 시 이전 검색 결과 목록을 초기화하고 선택한 출발지 이름을 표시합니다.
선택한 출발지는 같은 탭에서 새로고침해도 복원합니다.

검색은 카카오 지도 SDK의 장소 검색 기능을 사용하지만,
출발지 선택 영역에 지도나 마커를 생성하지 않습니다.

‘여행지 자료 등록’은 DB에 등록된 장소라는 뜻입니다.
장소 전체의 무장애 이용을 보장하는 표시는 아닙니다.

## 2. 개발 실행

Python 3.12 가상환경 `.venv`와 Node.js·npm을 사용합니다.
아래 명령은 프로젝트 루트에서 실행하는 Windows CMD 기준입니다.

**최초 설치 또는 의존성 변경 시**

```cmd
.venv\Scripts\python.exe -m pip install -r requirements.txt
npm ci
npm --prefix frontend ci
```

루트와 프론트는 각각의 `package.json`과 잠금 파일을 사용합니다.

**환경변수**

| 파일 | 변수 |
|---|---|
| 루트 `.env` | `KAKAO_REST_API_KEY`, `OPENAI_API_KEY` |
| `frontend/.env.local` | `VITE_KAKAO_MAP_KEY`: 지도 SDK용 JavaScript 키 |

실제 키는 Git에 포함하지 않습니다.
지도 앱의 허용 도메인에 `http://localhost:5173`을 등록합니다.
교통·LLM API 키는 백엔드에서 사용합니다.

**백엔드·프론트 통합 실행**

```cmd
.venv\Scripts\activate.bat
npm run dev
```

루트 실행 스크립트가 백엔드와 프론트를 함께 실행합니다.
백엔드는 활성화한 Python 환경을 사용하며,
실행 명령에 `-X utf8`을 적용합니다.

서버를 실행한 터미널은 켜 둡니다.
lint와 build 명령은 개발 서버를 실행하지 않습니다.

| 주소 | 용도 |
|---|---|
| `http://localhost:5173` | 프론트 화면 |
| `http://127.0.0.1:8000/docs` | 자동 API 명세 |
| `http://127.0.0.1:8000/health` | 백엔드 상태 확인 |
| `http://localhost:5173/api/health` | 프론트 프록시를 통한 상태 확인 |

Vite 개발 서버는 `/api` 요청을 백엔드로 전달하면서 접두사를 제거합니다.
환경변수를 변경하면 해당 개발 서버를 재시작합니다.

## 3. 대화·장소 상세·사진·숙소 검색 API

**대화 요청**

브라우저는 `POST /api/chat`, 백엔드는 `POST /chat`을 사용합니다.
기존 `POST /plan`의 규격은 [기존 API 명세](api.md)를 참고합니다.

최소 요청 예시입니다.

```json
{
  "message": "제주에서 산책할 만한 곳을 알려 주세요."
}
```

사용자 메시지는 한 번에 1~1,000자입니다.

| 요청 필드 | 내용 |
|---|---|
| `message` | 현재 사용자 요청입니다. |
| `options` | 현재 선택 조건입니다. 생략할 수 있습니다. |
| `history` | 이전 대화입니다. 프론트는 전송 완료된 최근 20개 메시지를 전달합니다. |
| `current_plan` | 이전 응답의 `plan`입니다. 일정 수정 요청에 사용합니다. |

선택 조건은 다음과 같습니다.

| 구분 | API 필드 |
|---|---|
| 출발지 | `departure`, `departure_latitude`, `departure_longitude`. 좌표는 둘 다 보내거나 둘 다 비웁니다. |
| 여행 기간 | `start_date`, `trip_days`. 프론트에서 선택한 두 날짜로 일수를 계산하며, 일수는 1 이상의 정수입니다. |
| 이동 조건 | `transport`: `driving`·`walking`·`transit`, `mobility_aid`: `wheelchair`·`stroller`·`none` |
| 취향·필요 시설 | `travel_styles`, `requirements` |
| 귀환 | `return_to_origin`. 선택 UI는 제거했으며 자연어 요청과 기존 데이터 처리를 위해 유지합니다. |
| 숙소 상태 | `lodging_status`: `undecided`(미정), `provided`(숙소 정보 제공), `not_needed`(숙박 불필요), 미입력은 `null` |
| 숙박일별 숙소 | `lodging_stays`: `night`, `name`, `address`, `latitude`, `longitude`, 선택적인 `provider_place_id`·`place_url` 목록 |

미선택 값은 `null` 또는 빈 배열로 표현합니다.

`night=N`은 N일차 관광 후의 숙소이며 1 이상, `trip_days` 미만입니다.
같은 숙박일의 선택은 중복될 수 없습니다. 숙소 이름은 1~200자,
주소는 최대 300자이며 좌표는 제주 검색 범위의 유한한 수입니다.
숙소가 선택되어 있으면 상태는 `undecided` 또는 `provided`여야 합니다.
`undecided`에는 일부 숙박일만 선택한 경우도 포함합니다.
`provided` 역시 모든 숙박일을 선택했다는 보장은 아니며 비어 있는 숙박일은 미정으로 남깁니다.

대화 응답이 기존 숙소 상태를 빠뜨리면 이전 상태와 유효한 숙박일 선택을 유지합니다.
명시적인 상태 변경은 존중하며 여행 기간을 줄이면 범위를 벗어난 선택을 제거합니다.
사용자가 아직 숙소를 정하지 않았거나 숙소를 입력하지 않은 경우에도 관광 일정을 먼저 생성하도록 지시합니다.


`travel_styles`의 값은 `자연`, `해변`, `박물관·전시`, `산책로`, `공원`, `시장`입니다.
`requirements`는 `step_free`, `accessible_toilet`, `accessible_parking`입니다.

시작·종료 시각과 휴식 요청은 `message`에 작성합니다.
`/chat`의 선택 조건에는 별도 시간·휴식 필드를 보내지 않습니다.

**대화 응답**

| 응답 필드 | 내용 |
|---|---|
| `reply` | Agent 답변·추가 질문·변경 요약 |
| `options` | 이번 대화까지 반영한 현재 조건 |
| `plan` | 생성·수정한 전체 일정. 질문이나 일반 답변이면 `null` |
| `map_routes` | 최종 일정에 연결되고 검증된 지도 경로 목록 |
| `transit_routes` | 이번 실행에서 최종 버스 이동에 연결한 구간별 안내. 경로선 좌표 유무와 별도로 제공합니다. |
| `warnings` | 확인이 필요한 항목과 지도 경로 누락 안내 |
| `meta` | 실행한 시도들의 모델·도구 호출 횟수 합계와 전체 처리시간 |

일정 항목은 방문인 `visit`과 이동인 `move`로 구분합니다.
이동 항목의 `route_id`로 해당 지도 경로와 버스 안내를 연결합니다.

`transport`에는 일반 이동수단명만 작성하도록 지시합니다.
예외적으로 `버스 102번(승차·하차 설명)`처럼 노선 번호가 붙은 표기는
ScheduleItem 입력에서 `버스`로 정리하며, 중첩된 정류장 이름의 괄호도 처리합니다.
모호한 복합 이동수단과 불완전한 설명은 임의로 해석하지 않습니다.
경로 ID·조회 수단·이동시간 대조는 기존 기준으로 계속 적용합니다.

일정의 시간 형식·겹침·소요시간과 요청한 일차의 수·순서를 검증합니다.
새 일정의 이동 항목은 이번 Agent 실행의 조회 기록과 추가로 대조합니다.

| 검증 항목 | 기준 |
|---|---|
| 경로 ID | 모든 이동에 이번 실행에서 조회한 `route_id`가 있어야 합니다. 조회 기록의 중복 ID와 여러 이동에 재사용한 ID는 거부합니다. |
| 이동수단 | 일정 항목의 이동수단 표기를 정규화한 뒤 해당 조회 기록의 이동수단과 비교합니다. |
| 이동시간 | 조회 결과의 초 단위를 분으로 올림한 값과 비교하며 ±1분을 허용합니다. |

각 시도에서 이 검증은 장소 DB 조회 전에 실행합니다.
첫 검증 실패에는 아래 자동 재생성 규칙을 적용하며,
최종 실패하면 HTTP 502 `plan_validation_failed`를 반환합니다.
오류 응답은 `error.code`, `error.message`, `error.details` 구조입니다.

실패한 새 일정은 반환하지 않으며, 화면은 이전에 받은 일정을 유지합니다.
질문 응답과 이전 저장 일정의 입력에는 새 이동 검증을 적용하지 않습니다.
후속 요청으로 전체 일정을 다시 생성하면 새 결과의 모든 이동을 검증합니다.

**장소명 검색과 누락 ID 보완**

Agent는 주변 추천에 `search_places`,
특정 장소 이름 조회에 `search_places_by_name`을 사용합니다.
이름 검색은 기본 5개, 최대 10개의 후보를 반환합니다.

공백·대소문자·한글 유니코드 표기를 정규화한 이름 일치는 `exact`,
이름 일부가 겹치는 후보는 `partial`로 구분합니다.
부분 일치나 동명 후보를 이름만으로 같은 장소라고 확정하지 않습니다.

`/chat`에서는 시간·일차·이동 검증 이후 누락된 방문 장소 ID를 보완합니다.

| 조건 | 처리 |
|---|---|
| 이번 실행에서 검색과 상세 조회를 모두 성공함 | 보완 근거로 사용합니다. 상세 조회의 요청 ID와 응답 ID도 같아야 합니다. |
| 일정 이름과 상세 조회 이름이 정규화 후 일치하고, DB에서도 같은 이름의 후보가 하나임 | 누락된 `place_id`를 보완합니다. |
| 부분 일치·동명 후보·근거 부족 | ID를 임의로 채우지 않고 기존 미확인 안내를 유지합니다. |
| 기존 ID가 있음 | 보완으로 덮어쓰지 않고 기존 DB 검증을 적용합니다. |
| 보완에 필요한 DB 조회 실패 | HTTP 500 `internal_error`를 반환합니다. |

질문 응답에는 ID 보완을 적용하지 않습니다.
이전 대화와 저장된 일정은 이번 실행의 조회 근거로 사용하지 않습니다.
보완된 ID를 포함해 각 방문일의 휴무 여부를 검사합니다.
휴무일 방문이 있으면 해당 시도의 검증을 실패로 처리합니다.
방문 종료 시각이 그날 닫는 시각(계절별 운영시간은 방문 날짜의 달)보다 늦어도 실패로 처리합니다.
자동 재생성 후에도 검증에 실패하면 HTTP 502 `plan_validation_failed`를 반환합니다.
이 검사를 통과하면 기존 DB 검증으로 장소명과 좌표를 확정합니다.
시간·일차·이동 검증에 실패하면 ID 보완과 휴무일·운영시간 DB 조회는 수행하지 않습니다.

두 Agent 모두 이름 검색을 지원하지만,
누락 ID의 서버 보완은 `/chat`에만 적용했습니다.

평가의 H5는 두 검색 도구의 결과를 모두 검색 근거로 인정합니다.
평가 스크립트는 Agent 원본 응답을 평가하므로,
`/chat`에서 ID를 보완한 뒤의 응답과 평가 결과가 다를 수 있습니다.

**경로 출발·도착 좌표 검증**

`/chat`은 DB에서 방문 장소의 이름과 좌표를 확정한 뒤,
지도 경로를 응답에 넣기 전에 `validate_route_endpoints`를 실행합니다.

| 검증 대상 | 기준 |
|---|---|
| 방문 장소 앞뒤의 이동 | `verified: true`인 방문 장소의 DB 좌표와 해당 이동의 요청 좌표를 대조합니다. |
| 연속 이동 | 직전 이동의 도착 좌표와 다음 이동의 출발 좌표를 대조합니다. |
| 최초 출발 | 유효한 출발지 좌표가 있으면 1일차 첫 이동의 출발 좌표와 대조합니다. |
| 최종 귀환 | 출발지 귀환 조건이 true이고 좌표가 있으면 마지막 일차의 마지막 이동 도착 좌표와 대조합니다. |
| 선택한 숙소 | N번째 숙박일의 위치를 N일차 마지막 이동의 도착과 N+1일차 첫 이동의 출발 좌표에 대조합니다. |

좌표 간 직선거리가 100m 이내이면 허용합니다.
비교에는 길찾기에 전달한 좌표를 사용하며 도로선 `paths`는 사용하지 않습니다.
확인되지 않은 방문 장소나 기준 좌표가 없는 끝점은 검사에서 제외합니다.
여러 날의 일정을 매일 같은 출발지에서 시작한다고 가정하지 않습니다.

불일치하거나 비교할 경로 좌표가 잘못되면 해당 시도의 검증을 실패로 처리합니다.
자동 재생성 후에도 검증에 실패하면 HTTP 502 `plan_validation_failed`를 반환합니다.
실패한 새 일정과 지도 경로는 반환하지 않으며, 화면은 이전 결과를 유지합니다.

질문 응답과 기존 저장 일정의 입력에는 적용하지 않습니다.
후속 요청으로 생성한 새 일정은 다시 검사합니다.
기존 `/plan`에는 이번 좌표 검증을 적용하지 않았습니다.

**검증 실패 후 자동 재생성**

`/chat`은 최초 생성 후 일정 검증에 실패하면 최대 한 번 다시 생성합니다.
Agent 실행은 총 두 번까지이며, 한 실행 안의 모델 호출은 여러 번일 수 있습니다.

| 상황 | 처리 |
|---|---|
| 시간·일차·경로 ID·이동수단·이동시간·휴무일·운영시간·경로 좌표 검증 실패 | 첫 실패 이유를 전달해 최대 한 번 전체 일정을 재생성합니다. |
| 재생성 결과가 다시 검증에 실패하거나 고정된 조건을 변경함 | 추가 재생성 없이 HTTP 502 `plan_validation_failed`를 반환합니다. 조건 변경의 오류 상세 필드는 `options`입니다. |
| 입력·DB·외부 서비스 오류 또는 AI 응답 형식 오류 | 자동 일정 재생성 없이 기존 오류 처리를 적용합니다. |
| 질문 응답·필수 정보 부족·검증을 통과한 빈 일차 | 자동 재생성 대상이 아닙니다. |

재생성 요청은 원래 메시지·대화 기록·선택 옵션·기존 일정을 유지한 채
마지막 사용자 JSON에 `plan_retry`를 추가합니다.
`locked_options`는 첫 시도에서 정리한 조건이며, 재생성 결과와 비교합니다.
출발지와 좌표·날짜·기간·이동수단·보조기구·여행 종류·필수 조건·귀환·숙소 상태·숙박일별 숙소를 유지합니다.
여행 종류·필수 조건 목록과 숙박일별 숙소 목록의 순서만 다른 경우는 허용합니다.

실패한 일정에서는 경로 ID와 DB 확인 표시·좌표를 제거해 참고 자료로만 전달합니다.
장소와 이동은 이번 실행에서 다시 확인하도록 지시하며,
첫 시도의 경로 기록과 도구 응답을 두 번째 시도의 검증 근거로 합치지 않습니다.
오류 피드백은 최대 20개이며 각 이유는 500자까지 전달합니다.

재생성 결과도 동일한 전체 검증을 통과해야 합니다.
조건을 유지한 질문 응답은 `plan: null`로 반환할 수 있습니다.
유효한 새 일정이 없으면 화면은 이전 결과를 유지합니다.

정상 응답의 `meta`에는 응답을 받은 각 시도의 모델·도구 호출 횟수를 합산하고,
`elapsed_seconds`에는 전체 처리시간을 기록합니다.
외부 통신 재시도는 기존 모델 설정을 따르며, 자동 일정 재생성과 구분합니다.
이 기능은 `/chat`에 적용하며 기존 `/plan`과 Agent 직접 평가 실행에는 적용하지 않습니다.

**버스 승하차 안내**

`transit_routes`는 `route_id`, `requested_at`, `segments`를 제공합니다.
`segments`는 선택된 전체 경로의 버스·도보·미확인 구간 순서를 유지합니다.

| 구간 필드 | 내용 |
|---|---|
| `type` | `BUS`, `WALKING`, `UNKNOWN` |
| `distance_m`, `duration_seconds` | 확인된 구간 거리와 소요시간. 없거나 잘못된 값은 `null` |
| `route_numbers` | 같은 버스 구간에서 이용 가능한 노선 목록. 화면에서는 '또는'으로 구분 |
| `boarding_stop`, `alighting_stop` | 승차·하차 정류장명. 미확인은 `null` |
| `ride_stop_count` | 승차지는 제외하고 하차지는 포함한 이동 정거장 수. 미확인은 `null` |

정거장 수는 [카카오 대중교통 경로 응답](https://developers.kakao.com/docs/ko/kakaomap/rest-api)의
정류장 목록을 사용합니다. 승하차 이름과 목록의 양 끝이 일치하고
유효한 이름이 2개 이상이면 목록 길이에서 1을 뺍니다.
이름이 같은 정류장도 목록의 각 위치를 유지합니다.
빈 목록·잘못된 이름·승하차 불일치는 정거장 수를 추정하지 않습니다.

Agent용 기존 버스 요약의 `stop_count`는 승차지를 포함한 목록 길이를 유지합니다.
화면용 `ride_stop_count`와 실시간 도착 차량의 `remaining_stops`는 서로 다른 값입니다.

버스 지도 도구가 이미 선택한 경로에서 안내를 기록하므로,
이 정보를 만들기 위해 외부 API나 AI를 추가 호출하지 않습니다.
최종 일정에서 사용하는 유일한 경로 ID와 이동수단이 일치하는 기록만 노출합니다.
첫 실패 후 재생성하면 두 번째 실행의 기록만 사용합니다.
지도 좌표가 없어도 안내는 제공하며, 이전 저장 일정에 안내가 없으면 미확인으로 표시합니다.

**주변 숙소 검색과 선택**

관광 일정을 생성한 뒤 숙박일별 일정표 위의 '주변 숙소 보기'를 누릅니다.
그날 마지막 방문지가 DB로 확인되고 좌표가 있을 때 반경 5km 안의 후보를 최대 5개 조회합니다.
마지막 방문지가 미확인이면 앞선 관광지나 원래 출발지를 임의의 검색 기준으로 대신하지 않습니다.
마지막 여행일과 숙박 불필요 상태에는 숙소 선택 영역을 표시하지 않습니다.

후보는 기존 관광지 DB와 구분한 [카카오 로컬 숙박 분류(AD5) 검색](https://developers.kakao.com/docs/ko/local/dev-guide)을 사용합니다.
AI 추가 호출 없이 목록을 조회하고, 사용자가 선택하면 위치를 선택 옵션에 넣어 후속 대화 요청을 보냅니다.
숙소 검색 식별값을 관광지 DB의 `place_id`로 사용하거나 숙소를 관광지 `visit`으로 만들지 않습니다.

| API | 내용 |
|---|---|
| 백엔드·프록시 주소 | `GET /lodgings/nearby`, 브라우저는 `GET /api/lodgings/nearby` |
| 필수 검색 위치 | `latitude`: 33.10~33.60, `longitude`: 126.08~127.00 |
| 검색 범위·개수 | `radius_m`: 1~20,000m, 기본 5,000. `max_count`: 1~10, 기본 5 |
| 응답 공통 정보 | `source: kakao_local`, 시간대가 있는 `requested_at`, 요청과 같은 `center`·`radius_m`, `places` |
| 후보 항목 | `provider_place_id`, `name`, `address`, `phone`, `latitude`, `longitude`, `distance_m`, `place_url` |
| 후보 없음 | HTTP 200과 빈 `places`를 반환하며 검색 위치와 조회 시각은 유지합니다. |
| 오류 | 입력 400 `invalid_request`, 한도 초과 429 `lodging_search_rate_limited`, 설정·인증 503 `lodging_search_unavailable`, 검색·응답 502 `lodging_search_failed` |

`distance_m`는 기준 좌표에서 후보까지의 직선거리이며 도로 이동 거리가 아닙니다.
지도 링크는 후보 식별값과 일치하는 `https://place.map.kakao.com/` 주소만 허용합니다.
검색 중복·제주 범위 밖 좌표·숙박 이외 분류·반경 밖 후보는 제외합니다.
API 키와 내부 필드는 응답에 넣지 않으며 가격·잔여 객실·접근성을 확인한 값으로 만들어 넣지 않습니다.

서버의 숙소 검색 통신 제한은 20초, 프론트 대기시간은 25초입니다.
날짜 전환 등으로 조회 영역이 사라지면 프론트 요청을 취소하고 늦게 도착한 결과를 적용하지 않습니다.
검색 실패는 기존 관광 일정과 지도를 유지한 채 안내하며 재조회할 수 있습니다.

선택은 예약이 아니라 일정의 기준 위치를 지정하는 동작입니다.
사용자가 입력한 선택 또는 현재 메시지에서 이름·주소로 지목하고 이번 실행의 `find_location`으로 확인한 위치만 새 숙소 근거로 인정합니다.
이전부터 선택한 동일 숙박일의 숙소는 유지할 수 있으며, 새 숙소를 AI가 임의로 선택하는 것은 거부합니다.
위치 조회 근거와 좌표를 비교할 때 소수점 반올림에 따른 0.000001도 이내의 차이만 허용합니다.

숙소가 없는 일차의 첫·마지막 이동 때문에 관광 일정 전체를 거부하지 않습니다.
서버는 숙소 미정일 때 첫 관광지 앞의 이동과 마지막 관광지 뒤의 이동만 제외한 뒤
남은 일정의 시간·경로 ID·이동수단·이동시간·휴무일·운영시간·끝점을 검증합니다.
최초 여행 출발, 마지막 날 최종 이동, 관광지 사이 이동과 선택한 숙소 이동은 제외하지 않습니다.
방문이 없는 일차는 임의 정리하지 않으며, 원래 입력과 방문 시각·체류시간은 변경하지 않습니다.
제외한 이동은 지도 경로·버스 안내에도 노출하지 않고 답변·확인사항·전제에 제외 사실과 시간 재계산 필요를 표시합니다.

숙소를 선택하거나 취소하면 기존 관광 조건을 포함해 전체 일정을 다시 요청합니다.
새 일정이 실패하면 이전 지도·일정은 유지하고 선택 옵션과 재전송 요청을 남깁니다.
지도에는 전날 숙소의 출발, 당일 숙소의 도착, 마지막 날 원래 출발지 귀환을 구분합니다.
숙소가 미정인 둘째 날 이후에 원래 출발지를 자동으로 숙소 출발점처럼 표시하지 않습니다.

**장소 상세 API**

백엔드는 `GET /places/{place_id}/details`,
브라우저는 `GET /api/places/{place_id}/details`를 사용합니다.
장소 ID는 공백 제거 후 1~80자입니다. 기존 DB 조회 도구를 사용하며 AI는 호출하지 않습니다.

| 응답 필드 | 내용 |
|---|---|
| `place_id`, `name` | 확인한 장소 ID와 DB 이름 |
| `category` | 장소 분류. 미등록은 `null` |
| `closed_days` | 등록된 휴무 정보 또는 '확인 안 됨' |
| `spots` | 지점 이름 `name`과 접근 동선 설명 `description` |
| `accessibility_facts` | 조사 원문의 `section`, `facility_name`, `description`, `raw_value` |

다른 장소 ID나 잘못된 성공 응답은 정상 결과로 전달하지 않습니다.
입력 오류는 400 `invalid_request`, 없는 장소는 404 `place_not_found`,
DB·응답 오류는 500 `internal_error`입니다.
서버의 파일 경로나 응답 모델 밖의 내부 필드는 포함하지 않습니다.

**상세 창과 일정표**

일정표는 시간·일정·소요시간 세 칸으로 표시합니다.
방문별 `accessibility_notes`는 장소 상세 창의 '이번 일정의 접근성 안내'에 표시합니다.
같은 장소를 여러 번 방문해도 클릭한 방문 항목의 메모만 전달합니다.
이 메모는 일정 생성 시 작성된 안내이며 아래의 조사 원문과 구분합니다.
상세 조회가 실패하거나 자료 연결이 미확인이어도 기존 메모를 표시합니다.
이동 항목의 메모는 일정표에서 '이동 시 확인사항'을 펼쳐 확인합니다.

시설·추천 원문은 조사 분류와 시설명이 모두 같은 항목끼리 묶습니다.
시설명이 다른 주차장이나 화장실의 내용을 합치지 않으며,
빈 이름은 미등록으로 안내하고 추천 기호를 등급으로 바꾸지 않습니다.
'미설치'라는 조사 원문과 표시할 자료가 없는 상태를 구분합니다.
지점별 설명은 각 지점 이름을 펼쳐 읽습니다.

'시설·동선 정보'와 '사진' 버튼으로 보기를 전환합니다.
두 조회는 독립적으로 실행하고, 각각 재시도할 수 있습니다.
사진이 없어도 시설 정보를 표시하며, 실패한 한 요청이 다른 결과를 숨기지 않습니다.
각 요청의 대기시간은 15초이며 창을 닫으면 진행 중인 요청을 취소합니다.
닫기 버튼과 Esc로 창을 닫으면 기존 일정·지도와 선택한 일차를 유지하고
장소 버튼으로 초점을 돌려줍니다.

**사진 API**

아래 경로는 백엔드 기준입니다.
브라우저에서는 앞에 `/api`를 붙여 요청합니다.

| 요청 | 응답 |
|---|---|
| `GET /places/{place_id}/images` | 장소 이름과 사용 가능한 사진 목록 |
| `GET /places/{place_id}/images/{image_id}` | 해당 사진 파일 |

사진 목록에는 `image_id`, `url`, `caption`, `alt`를 제공합니다.
서버의 로컬 파일 경로는 응답에 포함하지 않습니다.

DB에 기록된 장소는 있지만 사진 파일이 없으면 정상 응답으로 빈 목록을 반환합니다.

```json
{
  "place_id": "P001",
  "name": "한림공원",
  "images": []
}
```

장소나 사진이 없으면 404, DB 조회 오류는 500으로 반환합니다.

사진 조회는 일정 생성과 별도로 실행합니다.
창을 닫으면 진행 중인 목록 요청을 취소하며, 조회 제한 시간은 15초입니다.
사진 조회 오류가 나도 기존 대화·일정·지도는 유지합니다.

**사진 파일 위치와 현재 상태**

`place_spots`의 `source_file`, `image_file`을 사용합니다.
기록된 CSV와 같은 폴더에 실제로 존재하는 사진만 제공합니다.

예를 들어 다음 기록이라면:

```text
source_file: data/raw/jeju_datahub/hub_1/001-2.csv
image_file: 001_DSC00236.jpg
```

찾는 파일은 다음 위치입니다.

```text
data/raw/jeju_datahub/hub_1/001_DSC00236.jpg
```

원본 폴더 밖의 경로와 지원하지 않는 확장자는 제외합니다.
지원 확장자는 JPG·JPEG·PNG·WEBP·GIF입니다.
원본 사진에는 기존 `data/raw`의 Git 제외 규칙이 적용됩니다.

현재 프로젝트에는 실제 사진 파일이 없습니다.
원본 보관처를 확인하고 DB에 기록된 경로와 연결한 뒤,
정상 사진 표시와 실제 파일 전송을 추가 검증해야 합니다.

## 4. 지도 경로 연결

**처리 흐름**

| 단계 | 처리 |
|---|---|
| 조회 | 자동차·도보·버스 도구가 이동시간과 경로를 조회합니다. |
| 기록 | `backend/app/tools/map_transport.py`에서 조회마다 고유 `route_id`를 만들고 좌표를 이번 요청의 기록에 보관합니다. |
| 일정 연결 | Agent는 도구가 반환한 ID를 해당 `move.route_id`에 넣습니다. 대량의 경로 좌표는 Agent 응답에 넣지 않습니다. |
| 이동 일관성 검증 | `backend/app/services/plan_consistency.py`에서 새 일정의 경로 ID·이동수단·이동시간을 이번 실행의 조회 기록과 대조합니다. |
| 응답 선택 | `backend/app/services/plan_routes.py`에서 최종 일정이 참조한 이번 실행의 경로만 검증해 반환합니다. |
| 화면 표시 | `frontend/src/services/itineraryRoutes.js`에서 선택한 일차의 경로를 고르고, `ItineraryMap.jsx`에서 선으로 표시합니다. |

하나의 경로 ID는 하나의 이동 항목에만 연결합니다.
후속 요청에서는 이전 일정의 ID를 Agent 입력 사본에서 비우고,
유지하는 이동도 이번 실행에서 다시 조회하도록 합니다.
브라우저에 저장된 이전 일정 자체는 변경하지 않습니다.

버스 도구는 환승 횟수가 가장 적고, 같으면 소요시간이 짧은 경로를 선택합니다.
버스 요약과 지도 좌표는 같은 선택 경로를 사용합니다.
지도 좌표를 얻기 위해 카카오 경로를 별도로 재조회하지 않습니다.

버스 도구의 ID는 환승과 도보를 포함한 전체 이동 경로를 가리킵니다.
이 조회 결과는 일정의 이동 항목 하나에 연결하며,
포함된 도보 시간을 다시 더하지 않습니다.

**이동수단별 표시**

| 이동수단 | 좌표 처리 | 표시 |
|---|---|---|
| 자동차 | 도로별 `vertexes`를 좌표 쌍으로 변환하고 도로별 경로를 유지합니다. | 파란 실선 |
| 도보 | 안내 단계별 `path_points`를 별도 경로로 유지합니다. | 초록 점선 |
| 대중교통 | 선택 경로의 버스·도보 단계별 `path.points`를 유지합니다. | 전체 경로를 주황 실선으로 표시합니다. |

경로 좌표는 WGS84의 `[경도, 위도]` 순서입니다.
지도 SDK에는 `LatLng(위도, 경도)` 순서로 전달합니다.
서로 분리된 경로 사이에 임의의 직선을 만들지 않습니다.

지도 경로는 `route_id`, `transport`, `origin`, `destination`,
`distance_m`, `duration_seconds`, `geometry_status`, `paths`, `requested_at`을 제공합니다.

`requested_at`은 서버가 경로 조회를 시작한 시각이며,
제공기관의 갱신 시각과 구분합니다.
지도에는 조회 시각을 한국 시간으로 표시합니다.

오른쪽 일정 지도는 마우스 휠로 확대·축소할 수 있습니다.
일정이 있으면 화면 너비와 관계없이 지도는 왼쪽, 일정표는 오른쪽에 표시합니다.
두 영역의 최소 너비 합계보다 공간이 좁으면 결과 내부에서 가로로 스크롤합니다.
지도와 일정표를 위아래로 전환하거나 페이지 전체를 가로로 늘리지 않습니다.
결과 칸이 좁을 때는 가로 스크롤과 옵션 접기를 안내합니다.

일차 선택 버튼은 지도와 일정표 위에 함께 표시합니다.
일차를 변경하면 해당 날짜의 지도와 일정표를 함께 전환하고,
일정표는 맨 위부터 표시합니다.
좌우 배치에서는 일정표를 스크롤하면서 지도를 함께 볼 수 있습니다.
‘전체 경로 보기’는 장소와 경로 전체가 화면에 들어오도록 범위를 조정합니다.
영역 너비가 바뀌면 지도 크기를 다시 계산하면서 중심 위치를 유지합니다.

**좌표 누락과 부분 실패**

| 상황 | 동작 |
|---|---|
| 새 일정의 경로 ID 누락·불일치·중복·재사용 | 새 일정을 반환하지 않고 502 오류를 안내합니다. 화면의 이전 일정은 유지합니다. |
| 새 일정의 이동수단·이동시간이 조회 결과와 불일치 | 새 일정을 반환하지 않고 502 오류를 안내합니다. 화면의 이전 일정은 유지합니다. |
| 일부 구간의 좌표가 잘못됨 | 이동 일관성 검증을 통과한 일정은 유지하고, 확인된 경로만 표시하며 안내합니다. |
| 좌표 없음·좌표 검증 실패 | 이동 일관성 검증을 통과한 일정은 유지하고, 해당 경로선만 제외합니다. |
| 제주버스 실시간 조회 일부 실패 | 확보한 카카오 경로 좌표와 정상 버스 정보를 유지합니다. |
| 이전 저장 일정에 지도 경로가 없음 | 장소와 일정표를 표시하며 경로선을 임의로 만들지 않습니다. |

저상 여부를 알 수 없는 값은 미확인 상태로 유지하며 `False`로 바꾸지 않습니다.
버스 차량의 실시간 위치 마커나 자동 갱신 지도는 구현하지 않았습니다.

## 5. 상태 복원과 영역 너비 조절

추가 질문만 반환되어 `plan`이 `null`이면 기존 지도와 일정을 유지합니다.
새 일정이 반환되면 전체 일정과 연결 경로를 교체합니다.

선택 옵션을 변경하면 다음 메시지에 함께 전달합니다.
그동안 기존 지도·일정은 생성 당시 조건을 기준으로 표시하고,
옵션이 변경된 경우 이전 결과임을 안내합니다.

응답 대기 중에는 메시지 입력과 옵션 변경을 잠급니다.
실패한 요청은 사용자가 다시 보낼 수 있습니다.

**대화와 일정**

같은 탭의 `sessionStorage`에 대화·옵션·일정·지도 경로·선택한 일차를 저장합니다.
숙소 미정 상태와 숙박일별 선택도 옵션에 저장하며, 이전 저장 대화에는 숙소 기본 필드를 보완합니다.
새로고침은 저장된 결과를 복원하며,
일정 생성이나 교통 경로 조회를 자동으로 다시 실행하지 않습니다.

응답 대기 중 새로고침한 요청은 실패 상태로 복원해 수동 재전송할 수 있게 합니다.
4일 이후의 일차도 저장·복원합니다.
과거 날짜가 포함된 기존 대화를 삭제하지 않으며,
출발일이 지났으면 날짜 재선택을 안내합니다.

‘새 여행 시작’은 대화와 여행 조건·결과를 초기화합니다.
사용자별 서버 대화 저장과 기기 간 동기화는 구현하지 않았습니다.

**영역 너비**

가로 901px 이상에서는 옵션·채팅·결과를 나란히 표시하고 경계선으로 너비를 조절합니다.
최소 너비는 옵션 220px, 채팅 280px, 결과 320px입니다.
옵션을 접으면 채팅과 결과 두 영역에 공간을 배정하고 두 영역 사이를 조절합니다.
가로 900px 이하에서는 바깥 영역을 세로로 배치하지만 지도와 일정표는 좌우 배치를 유지합니다.

옵션 패널 맨 위 오른쪽의 `<` 버튼으로 옵션을 접습니다.
접힌 상태에서는 왼쪽에 남은 `>` 버튼으로 다시 펼칩니다.
옵션 제목과 화살표는 고정하고 선택 항목만 세로로 스크롤하여, 화살표와 스크롤바가 겹치지 않도록 배치합니다.
화살표 버튼에는 '여행 옵션 접기'·'여행 옵션 펼치기' 접근성 이름과 펼침 상태를 제공합니다.
접은 배치에서는 다시 펼치기 버튼을 위한 좁은 공간을 제외하고 채팅·결과 너비를 계산합니다.
처음 화면에서는 옵션이 펼쳐져 있습니다. 접어도 선택한 조건과 출발지 검색 상태를 유지합니다.
옵션을 펼친 배치와 접은 배치의 너비 비율은 각각 저장합니다.

| 조작 | 동작 |
|---|---|
| 경계선 드래그 | 양옆 영역의 너비 조절 |
| Tab으로 경계선 선택 후 좌우 방향키 | 너비 조절. Shift를 누르면 더 큰 단위로 이동 |
| Home·End | 조절 가능한 최소·최대 위치로 이동 |
| 경계선 두 번 클릭 | 기본 너비로 초기화 |

옵션을 펼친 배치의 기존 기본 너비와 저장 설정을 유지합니다.
너비 비율은 `localStorage`의 `gachi-jeju.workspace-panels.v4`에 저장합니다.
접은 배치의 비율은 `gachi-jeju.workspace-panels.collapsed.v1`에 별도로 저장합니다.
사용자가 조절한 너비는 새로고침해도 복원하지만 옵션은 처음에 펼친 상태로 표시합니다.

영역 너비는 ‘새 여행 시작’과 별도로 관리합니다.
저장소를 사용할 수 없어도 현재 화면의 너비 조절은 동작합니다.

가로 900px 이하에서는 너비 조절 경계선을 숨깁니다.
브라우저 확대나 창 크기 변경 시 실제 표시 너비에 맞춰 배치를 다시 계산합니다.

| 이동수단 오류 | 첫 요청은 이동수단 대조에서 거절됐고 재시도는 성공했습니다. 최초 실패의 비교값을 확보하지 못해 원인은 미확정입니다. 이후 오류에 일정 표기·해석 결과·조회 수단을 표시하도록 진단 정보를 보강했습니다. |

DB 등록 확인은 장소 전체의 접근성이나 운영시간을 보장하지 않습니다.

## 7. 제약사항과 남은 범위

| 구분 | 현재 범위 |
|---|---|
| 접근성·운영시간 | DB 등록, 경로 존재, 도보 `ACCESSIBLE` 옵션만으로 실제 휠체어 통행을 보장하지 않습니다. 지점별 근거와 미확인 사항을 구분하며, 실제 운영 여부도 별도 확인이 필요합니다. |
| 휴무일 | `get_place_details(visit_dates=...)`가 날짜별 `휴무`·`영업`·`확인 안 됨`을 돌려주고, `/chat`은 휴무일 방문을 `plan_validation_failed`로 막습니다. 170곳 중 29곳은 휴무일 정보가 없어 항목 메모에 '휴무일 확인 필요'로 남깁니다. 설날·추석·부처님오신날 날짜표는 2026~2028년만 있고, 대체공휴일·임시공휴일은 판정하지 않습니다. |
| 운영시간·관람료 | `get_place_details`가 `opening_hours`(정리 값)·`opening_hours_raw`(원문)·`admission_fee`(관람료 원문)를 돌려주고, `/chat`은 방문 종료 시각이 닫는 시각보다 늦으면 `plan_validation_failed`로 막습니다. 170곳 중 운영시간 61곳·관람료 88곳은 정보가 없어 '확인 안 됨'이고, 미확인 장소는 항목 메모에 '운영시간 확인 필요'로 남깁니다. 입장마감 시각은 지시문에만 있고 검증하지 않으며, 시설별 시간·공연 회차는 원문에만 있습니다. |
| 일정과 교통 정보 대조 | `/chat`의 새 일정은 시간표와 경로 ID·이동수단·이동시간을 검증합니다. DB로 확인된 방문 장소와 길찾기 요청의 출발·도착 좌표도 100m 허용 범위로 대조합니다. 기준 좌표가 없는 끝점은 검사하지 않으며, 도로선 전체의 정확성을 검증하는 기능은 아닙니다. 기존 `/plan`에는 이동 일관성과 좌표 검증을 적용하지 않았습니다. |
| 자동 재생성·대기시간 | 첫 시도에서 정리한 조건을 유지하며 최대 한 번 다시 생성합니다. 재생성도 기존 프론트 응답 대기시간 180초에 포함됩니다. 서버 전체 실행시간 제한과 클라이언트 취소 연동은 별도 범위입니다. 실제 자동 수정 분기의 관찰은 남아 있으며 현재 분기 검증은 mock 기준입니다. |
| 버스 상세 안내 | 조회한 경로에 포함된 정보만 제공합니다. 구간·정거장 수가 없으면 미확인으로 표시하며, 이전 저장 일정의 안내를 자동 재조회하지 않습니다. 당일 운행과 실제 승하차 위치는 별도 확인이 필요합니다. |
| 버스 실시간 정보 | 현재 조회된 도착 차량과 저상 여부를 미래 탑승 시점의 정보로 보장하지 않습니다. 정적 정류장 정보가 없는 노선은 제주버스 연동이 제한될 수 있습니다. |
| 장기 일정·숙박 | 입력의 3일 상한은 제거했습니다. 숙소 미정 관광 일정과 숙박일별 숙소 선택을 지원하며 자동차 1박 2일 흐름을 사용자에게 확인받았습니다. 긴 기간 전체의 실제 Agent 생성과 야간 이동은 미검증이며 모델 출력량·응답 시간의 영향을 받습니다. |
| 숙소 추천·예약 | 마지막 방문지 주변의 위치 후보를 제공합니다. 가격·잔여 객실·접근성·예약은 확인하거나 처리하지 않습니다. 다른 지역 검색과 반경·개수 조절은 현재 숙소 화면에 없으며 API에서 반경·개수를 지정할 수 있습니다. |
| 운영 환경 | 현재 검증은 로컬 개발 환경 기준입니다. 배포 환경의 API 연결과 사용자별 서버 저장·동기화는 별도 구성 범위입니다. |
