# 최종 /chat 응답 평가

검증일: 2026-11-17

서버가 최종 반환한 `/chat` 응답을 수집하고 평가합니다.
실제 실행에서는 서버의 검증·자동 재생성·숙소 처리를 거친 결과를 기록합니다.

기존 Agent 직접 평가와는 별도 도구입니다.
기존 평가 스크립트·사례·실험 기록은 유지합니다.
질문에 답하거나 기존 일정을 수정하는 연속 요청은 [연속 대화 평가](chat-multiturn-evaluation.md)를 사용합니다.

────────────────────────────────────────

## 1. 실행 방법

프로젝트 루트에서 실행합니다.
FastAPI 앱을 같은 프로세스에서 호출하므로 개발 서버를 켤 필요는 없습니다.

평가 전용 프로세스에서 순차 실행합니다.
실행 중인 서버 내부에 평가 함수를 연결해 사용하지 않습니다.

**사례 정의만 검사**

```cmd
.venv\Scripts\python.exe -B -m scripts.evaluate_chat_api
```

기본 모드는 사례 정의의 구조만 검사합니다.
실제 API 호출, 결과 파일 생성과 Git 상태 조회를 하지 않습니다.

**실제 사례 하나 실행**

```cmd
.venv\Scripts\python.exe -B -m scripts.evaluate_chat_api --run --case A01 --repeat 1 --label api-driving-check --reference-date 2026-11-16
```

기존 백엔드의 모델·외부 API 설정을 사용합니다.

| 옵션 | 동작 |
|---|---|
| `--run` | 실제 Agent와 필요한 외부 API를 호출합니다. |
| `--case` | 지정한 사례 하나만 실행합니다. 생략하면 12개 사례를 모두 실행합니다. |
| `--repeat` | 사례별 반복 수입니다. 기본값은 1입니다. |
| `--label` | 결과 폴더의 이름표입니다. 영문·숫자·밑줄·하이픈 1~64자를 사용합니다. |
| `--reference-date` | 상대 날짜 해석의 기준일입니다. 생략하면 실행 당시 한국 날짜를 사용합니다. |

사례별로 자동 재생성이 발생하면 Agent를 최대 두 번 실행합니다.
Agent 실행 한 번에도 여러 모델·도구 호출이 포함될 수 있습니다.

`--reference-date`는 날짜 해석의 기준이며 외부 API의 실제 조회 시각을 바꾸지는 않습니다.
평가 시점이 달라지면 사례의 여행 날짜와 기준일도 함께 확인합니다.

**저장한 실행 재채점**

```cmd
.venv\Scripts\python.exe -B -m scripts.evaluate_chat_api --rescore "outputs\chat_eval\api\20261116-203318-676756_api-driving-check" --label api-driving-rescore
```

저장 당시의 사례 정의와 응답을 사용해 새 결과 폴더에 기록합니다.
원본 폴더는 수정하지 않으며 Agent·외부 API를 호출하지 않습니다.

`--rescore`에는 `--cases`, `--reference-date`와 반복 수 변경을 함께 사용하지 않습니다.
`--case`로 저장된 사례 중 하나만 선택할 수 있습니다.

## 2. 사례 정의와 기대 결과

사례 파일은 `scripts/eval_cases/chat_api_cases.json`입니다.

| 필드 | 의미 |
|---|---|
| `case_id`, `description` | 사례 식별자와 설명입니다. |
| `request` | 실제 `/chat` 요청 본문입니다. |
| `expectation` | 기대 결과 유형과 필요한 HTTP 상태·오류 코드·빈 일차를 지정합니다. |
| `expected_options` | 의도적으로 변경하거나 정확히 유지해야 하는 옵션의 기대값입니다. |
| `time_window`, `review_points` | 전체 일정의 시간 범위와 별도 내용 검토 항목입니다. |

**결과 유형**

| 유형 | 판정 |
|---|---|
| `plan` | 모든 일차에 방문 항목이 있습니다. |
| `message` | 일정 없이 답변합니다. 질문인지 일반 안내인지는 내용 검토로 확인합니다. |
| `empty_plan` | 모든 일차에 방문 항목이 없습니다. |
| `partial_plan` | 일부 일차에 방문 항목이 없습니다. |
| `error` | 지정한 HTTP 오류 상태와 오류 코드가 일치합니다. |

잘못된 응답 구조는 내부적으로 `invalid_response`로 분류합니다.
이를 정상적인 기대 결과로 지정할 수는 없습니다.

**기대값 작성**

```json
{
  "expectation": {
    "outcome": "empty_plan",
    "empty_days": [1]
  }
}
```

빈 일정과 부분 일정에는 `empty_days`를 명시합니다.
오류 기대값에는 정확한 HTTP 오류 상태와 오류 코드를 지정합니다.

```json
{
  "expectation": {
    "outcome": "error",
    "http_status": 400,
    "error_code": "invalid_request"
  }
}
```

방문이 없는 일차는 이동 항목이 있어도 빈 일차로 분류합니다.
따라서 제외 이유와 불필요한 잔여 이동은 별도로 검토해야 합니다.
응답에 ‘제외’라는 단어가 있다는 사실만으로 제외 사유가 타당하다고 판정하지 않습니다.

`time_window`는 이동을 포함한 전체 일정의 허용 시간 범위입니다.
특정 장소의 고정 방문 시각이나 요청한 방문 시간은 `review_points`로 확인합니다.

## 3. 자동 검사 범위

| 구분 | 검사 내용 |
|---|---|
| 응답·기록 | HTTP 결과, 응답 모델, 기대 결과 유형, 시도 순서와 관찰 기록의 유효성을 검사합니다. |
| 날짜·시간 | 여행 일수, 항목 시간·겹침·소요시간과 지정한 전체 시간 범위를 검사합니다. |
| 장소 | DB 존재, `verified` 표시와 마지막 시도에서 확보한 장소 조회 근거를 검사합니다. |
| 이동 | 경로 ID·이동수단·이동시간과 확인 가능한 출발·도착 좌표를 대조합니다. |
| 선택 조건 | 날짜·이동수단·보조기구·필수 조건 등 입력한 선택 옵션의 유지를 검사합니다. |

**답변 설명 대조**

`reply_consistency`는 최종 `reply`와 `plan.assumptions`를 검사합니다.
귀환을 선택한 일정의 명시적 귀환 시각과, 대상을 특정할 수 있는 방문 시작 시각을
최종 일정과 대조합니다. 시각 뒤에 출발이 명시된 표현은 방문 시작으로 판정하지 않습니다.
출발지 이름·‘출발지’로 돌아온다는 명시적 시각도 대조합니다.
이 표현에서 ‘센터’는 출발지 이름이 ‘센터’로 끝나는 경우에만 출발지로 해석하며,
다른 숙소·장소로 돌아가는 표현은 원래 출발지의 귀환으로 판정하지 않습니다.

사용자가 숙소를 요청하지 않은 당일 일정과 `not_needed` 일정에서는
불필요한 숙소 미정 메모도 검사합니다.
`/chat`에서는 기존 최대 1회 재생성에 연결하고, 재채점에서는 자동 실패로 판정합니다.

모든 숙박일의 선택이 있는 경우에는 숙소가 미정이거나 제공되지 않았다는
명시적인 설명도 검사합니다. 일부 숙박일만 선택한 경우에는 이 추가 검사를 적용하지 않습니다.

공통 경로 끝점 검사는 전날 일정이 있고 전날 선택 숙소·출발지가 확인된 귀환 요청에서
마지막 날 귀환 이동의 누락도 검사합니다. 관광지 없이 귀환 이동만 있는 날짜는 허용합니다.

기간 확인처럼 서버가 직접 반환한 질문도 실행 관찰 기록에 포함될 수 있습니다.
이 경우 모델·도구 호출 수 0회는 실제 미호출 결과이며 관찰 기록 누락과 구분합니다.

질문처럼 `plan`이 없는 응답에는 이 검사를 적용하지 않습니다.
일차·방문 대상이 모호하거나 경계·부정 표현 등으로 시각을 확정하기 어려우면 추정하지 않습니다.
모든 자연어 설명을 검증하는 기능은 아니므로 내용 검토는 계속 필요합니다.

**시도별 근거**

재생성된 일정의 장소·경로 근거에는 마지막 시도의 기록만 사용합니다.
이전 시도의 근거로 최종 일정의 누락을 보완하지 않습니다.

호출 수 집계에는 기록된 모든 시도를 포함합니다.
관찰 기록 수집에 실패하면 정상 HTTP 응답이 있더라도 평가 근거가 불완전한 것으로 처리합니다.

HTTP 응답을 수집한 직후 시도 기록을 잠금 안에서 복사해 고정합니다.
취소·전체 시간 초과 이후 도착한 결과나 예외가 반환된 평가 기록을 바꾸지 않습니다.
Agent 실행 또는 관찰 정보 수집이 끝나지 않았다면 해당 시도는 `running`으로 남습니다.
완료 정보나 호출 수를 임의로 채우지 않으며, 미완료 기록은 평가 근거가 불완전한 것으로 처리합니다.
관찰 정보 수집 오류는 서버 응답 자체를 변경하지 않습니다.

**이동 검증 기준**

이동시간은 기존 검증과 같은 분 단위 올림 및 ±1분 허용 기준을 사용합니다.
좌표는 기준 좌표가 있는 끝점만 100m 범위로 대조합니다.
자동차·대중교통 일정에 필요한 도보 구간은 허용합니다.

**자동 통과의 한계**

자동 통과만으로 필요한 이동 항목이 모두 생성됐거나 자연어 요청 전체를 충족했다고 보장하지 않습니다.
도로선 전체의 정확성과 실제 접근 가능 여부도 보장하지 않습니다.

운영시간·필수 시설 검증은 실제 실행 시 `/chat` 처리에 포함됩니다.
다만 재채점에서 현재 서버의 검증·자동 재생성 파이프라인을 다시 실행하는 것은 아닙니다.

## 4. 결과 파일과 해석

결과는 `outputs/chat_eval/api/` 아래 새 폴더에 저장합니다.
폴더 이름에는 실행 시각과 `--label` 값이 포함됩니다.

| 파일 | 내용 |
|---|---|
| `metadata.json` | 실행 모드, 채점 코드의 커밋·변경 상태, 기준일과 재채점 원본 폴더입니다. |
| `runs.jsonl` | 요청·사례 정의·최종 HTTP 응답·시도별 근거·생성 설정입니다. 채점 전에 저장합니다. |
| `scores.jsonl` | 자동 검사 결과와 내용 검토 필요 여부입니다. |
| `summary.csv` | 사례별 결과·호출 수·처리 시간·실패 이유입니다. Windows에서 읽을 수 있도록 UTF-8 BOM을 사용합니다. |
| `report.md` | 답변·일정·확인사항과 내용 검토 항목입니다. |

시도별 경로 요약에서는 도로선 좌표를 제외합니다.
최종 HTTP 응답의 `map_routes`에는 반환된 도로선 좌표가 유지됩니다.

**호출 수와 처리 시간**

호출 수는 수집한 기록을 기준으로 집계합니다.
예외·취소·시간 초과로 관찰 기록이 누락되면 실제 호출·사용량보다 적게 집계될 수 있습니다.
기록된 호출 수가 0이라고 실제 호출이나 과금이 없었다는 뜻은 아닙니다.

평가 실행의 `elapsed_seconds`는 요청·응답 수집 구간의 경과시간입니다.
응답 이후 계속된 작업의 최종 종료 시각이나 과금 시간을 뜻하지 않습니다.

재채점 결과의 호출 수와 처리 시간은 원래 생성 당시의 값입니다.
재채점에서 새로 모델이나 이동 API를 호출했다는 뜻이 아닙니다.

**자동 검사와 내용 검토**

| 값 | 해석 |
|---|---|
| `automatic_passed=True` | 자동 검사 기준을 통과했습니다. |
| `requires_manual_review=True` | 답변·제외 사유·요청 충족 여부 등 별도 내용 검토가 필요합니다. |

내용 검토 필요 여부는 검토 완료 상태를 관리하는 필드가 아닙니다.
보고서를 읽어도 플래그가 자동으로 해제되지 않으므로 실제 검토 결과를 별도로 기록합니다.

서버 응답 오류와 평가 도구의 기록 수집·채점 오류는 구분합니다.
평가용 DB를 읽지 못한 상황을 서버의 일정 생성 실패와 같은 원인으로 처리하지 않습니다.

**종료 코드**

| 코드 | 의미 |
|---|---|
| `0` | 모든 실행이 자동 기준을 통과했습니다. 내용 검토는 남아 있을 수 있습니다. |
| `1` | 자동 기준을 통과하지 못한 실행이 있습니다. |
| `2` | 설정·결과 읽기·파일 저장 등에 문제가 있습니다. |
| `130` | 사용자가 실행을 중단했습니다. |

결과 폴더는 기존 `outputs/chat_eval/` Git 제외 규칙을 따릅니다.
이번 작업에서는 생성 결과를 Git에 추가하지 않습니다.

## 5. 재채점 시 주의사항

재채점은 현재 사례 파일 대신 실행 당시 저장한 사례 정의를 사용합니다.
원본 실행 기록은 보존하고 채점 결과를 새 폴더에 기록합니다.

장소 검사에는 현재 로컬 DB를 읽습니다.
따라서 DB나 채점 코드가 바뀌면 같은 응답의 점수가 달라질 수 있습니다.

재채점은 저장된 응답의 평가입니다.
현재 코드로 Agent를 다시 실행하거나 새로운 일정을 생성하는 기능은 아닙니다.
기존 Agent 직접 평가 로그는 새 기록 형식과 구분하며 그대로 재채점하지 않습니다.

새 사례·판정 기준은 기존 Agent 직접 평가와 다릅니다.
두 평가의 점수를 직접 비교해 성능 개선으로 해석하지 않습니다.
DB 조사값을 근거로 정한 기대 결과는 데이터가 갱신되면 함께 검토합니다.
